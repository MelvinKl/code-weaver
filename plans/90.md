# Issue #90 — One word for the plan's units: "step"; per-step completion logging; per-step report outcomes

## Summary

Align every plan-facing surface on one word for the plan's checklist units —
**step** (the planner template, the implementer template, the plan files'
section heading, the implement stage's log) — give the implement stage
per-step completion logging (a per-step line while steps remain open, a
full-step-count completion line only when the plan is fully tracked, the
plain line kept for the single-call stages), and make the final status report
render a stage that will re-run per step and a stage that is done as
"stage complete". The delta's test and documentation consequences ride
along: the two plan-stage tests that quote the renamed brownfield scenario,
the documented oracle counts (175 → 179 scenarios), the arc42/README
plan-unit wording, and the runtime re-embed.

## Description

The requirement delta this plan covers (standing in-place shape — all three
changed files existed at the run's baseline and changed in place, so the
brownfield clause does not apply; a normal implementation plan):

- **`requirements/implement.feature`** — the plan's units are reworded from
  *task* to *step* in the feature text and in four existing scenarios
  (two of them renamed), and four **new** scenarios are appended:
  1. a clean call with steps still open logs the per-step line
     (`stage 8 implementation: clean — step <done>/<total> of the plan
     done; <remaining> step(s) remain`), counted from the plan file's
     checkboxes, and no "stage complete" while any step remains open;
  2. a fully tracked plan logs the full step count before the stage
     completes (`stage 8 implementation: all <total> plan steps done —
     stage complete`), the only line that calls the stage complete;
  3. the single-call stages (extract, plan, review) keep the plain
     "clean — stage complete" line — the shared generation loop does not
     force one completion wording on every caller;
  4. the templates, the plan files and the stage log agree on one word —
     the plan's section heading is "Steps", the templates' instructions and
     the implement stage's log call the units steps, and the checkbox form
     (`- [ ]` / `- [x]`) is unchanged: the code that reads the plan keys on
     the checkbox, not the word.
- **`requirements/plan.feature`** — the plan-stage scenarios reword *task*
  to *step* (one scenario renamed: "…scopes its **steps** to the test
  references"); behaviour is unchanged.
- **`requirements/reporting.feature`** — "The final status report is the
  PR" gains two And lines: a stage that will re-run is reported per step —
  "step \<k\>/\<n\> done" for each of its finished steps; a stage that is
  done is reported "stage complete".

Consequences the plan must land with the code so the standing oracle stays
green: the two plan-stage tests that quote the renamed scenario (and assert
the old template/clause wording), the documented oracle counts in the README
and arc42 chapters (the tree grows by the four new scenarios: 175 → 179),
the plan-unit wording in arc42 chapter 6 and the README, and the
factory-workflow runtime re-embed (any change under `.github/scripts`,
`.github/actions` or `pi-prompts` requires `make embed`).

This plan itself models the target convention — its checklist heading is
**Steps** and its units are steps — the implement stage reads this plan
top-to-bottom and keys on the checkboxes, so it works identically.

## Acceptance Criteria

Each mapped to the Gherkin scenario it fulfils (new = no existing scenario
covers it; adjusted = a scenario the delta alters; ripple = an unchanged
scenario whose obligation the delta triggers).

1. `implement.feature::The implementation works the next open step and marks it done` — **adjusted** (renamed; body reworded *task* → *step*; the checkbox keying and the one-open-unit-per-call behaviour are unchanged).
2. `implement.feature::The implementation loops until every step is done or a cap is reached` — **adjusted** (renamed; body reworded).
3. `implement.feature::Implementation may only edit the current issue's plan` — **adjusted** (body reworded; name unchanged).
4. `implement.feature::An empty implementation on an already-implemented branch is a no-op, not an error` — **adjusted** (body reworded; name unchanged).
5. `implement.feature::A clean call with steps still open logs the per-step line, not a stage completion` — **new**.
6. `implement.feature::A fully tracked plan logs the full step count before the stage completes` — **new**.
7. `implement.feature::The single-call stages keep the plain completion line` — **new**.
8. `implement.feature::The templates, the plan files and the stage log agree on one word for the plan's units` — **new**.
9. `plan.feature::The plan is written in Jira ticket style` — **adjusted** ("ordered, atomic Tasks checklist … one task at a time" → "… Steps checklist … one step at a time").
10. `plan.feature::The plan describes how the requirements are fulfilled` — **adjusted** ("for each task … the task touches" → "for each step … the step touches"; name unchanged).
11. `plan.feature::A brown field plan scopes its steps to the test references` — **adjusted** (renamed from "…its tasks…"; body reworded).
12. `reporting.feature::The final status report is the PR` — **adjusted** (two And lines added: per-step reporting for a stage that will re-run, "stage complete" for a stage that is done; the standing lines stand).
13. `requirement-extraction.feature::The documented oracle counts match the requirements tree` — **ripple** (the tree grows to 179 scenarios; every documented count surface must read 179).
14. `implement.feature::The arc42 documentation is updated and complete`, `implement.feature::The README is kept current` — **ripple** (the arc42 and README plan-unit wording describes the changed requirements and must be reworded to "step").
