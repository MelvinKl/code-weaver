# Issue #67 — The report step's plumbing: bound from the shared module where it imports; on the local fallback definitions where it cannot

**Summary**

Stage 15's status-report step is inlined in `factory.yml` (the workflow is
self-contained — no composite actions to reference) and its body calls its
plumbing — the state dir, the state file, the log, the gh api, the branch
push — by bare name. The step acquires those names one of two ways:

1. **the import path** — the shared module (`common.py` from the runtime
   tree the report job's first step stashes to `$RUNNER_TEMP` before the
   first checkout) resolves, and its definitions bind the names for the
   body;
2. **the fallback path** — the module does not resolve (a consumer pinned
   to a factory ref that predates it, the legacy workspace-copy tree, a
   runner build whose path resolution breaks the import), and the body runs
   on the step's local fallback definitions.

Today the step's `import common` binds only the module name: on the import
path the five plumbing names the body calls stay unbound, so the step dies
with an undefined-name error before any of its report work has run. On this
runner build the import fails (the stage-contract harness documents that the
stashed path's `/./` segment breaks the scripts-dir resolution, and the
fallback is the path production takes), so the defect has stayed masked. The
two new scenarios make both paths explicit requirements: the import path
binds the names and the step completes its report; the fallback path stays
effective and completes the report as on the import path.

**Description**

The changed requirements are a delta in `requirements/reporting.feature`:
two **new** scenarios — "The report step's plumbing is bound on a runner
where the shared module imports" and "The report step's fallback plumbing
stays effective where the shared module cannot import" (a pure addition; no
standing scenario in the file is altered, so the file carries no **adjusted**
scenario).

Two boundaries the plan works around, both grounded in the tree:

- **The dual-path binding is undocumented in the arc42 set.** The set
  documents the stashed runtime tree (chapter 7's stage flow), the report
  component's responsibilities (chapter 6's building-block row) and the
  shared-plumbing component (chapter 6's row), but nowhere says how the
  inlined report step acquires its plumbing names — import vs. local
  fallback. Say so: the plan has the implementation record it in the rows
  that document that component (an extension of the documented stash
  mechanism, no contradiction with it).
- **The standing suite exercises the fallback path only.** The stage-contract
  harness forces `import common` to fail (it scrubs the scripts dir from
  `sys.path` and pops an already-imported `common` module) and asserts the
  report the fallback run completes. The import path has no test coverage
  and is broken in the current step source. The changed file's *standing*
  scenarios are covered by the standing stage-contract tests, which keep
  passing unchanged against the modified step source — the review's verdict
  scope (chapter 9's delta scope: every scenario of the feature files this
  run changed, standing and new alike) sees no red leaking from a stale pin.

**Acceptance Criteria**

- **AC-1** — where the shared module the report step imports resolves from
  the runtime tree, the step's plumbing names (the state dir, the state
  file, the log, the gh api, the branch push) are bound for the step's body:
  the step does not fail with an undefined-name error before any of its
  report work has run, and it completes its report on that path.
  *(Scenario "The report step's plumbing is bound on a runner where the
  shared module imports" — **new**; no existing scenario covers the import
  path)*
- **AC-2** — where the shared module does not resolve from the runtime
  tree, the report step's body runs on its local fallback definitions and
  completes its report as on the import path.
  *(Scenario "The report step's fallback plumbing stays effective where the
  shared module cannot import" — **new**; the "stays effective" half is
  already exercised by the standing stage-contract tests, which force the
  import failure and assert the fallback-completed report — the change adds
  the "as on the import path" equivalence)*

**Tasks**

- [x] **Task 1 — bind the report step's plumbing names on the shared-module
  import path.**
  The goal: in the report stage's inlined status-report step (the `run: |`
  block of the report job in `factory.yml`), where the step's
  `import common` succeeds — the module resolves from the runtime tree the
  job's first step stashed to `$RUNNER_TEMP` — bind the five plumbing names
  the body calls by bare name (the state dir, the state file, the log, the
  gh api, the branch push) from the shared module into the step's own scope,
  so the body's bare-name calls resolve on that path and the step completes
  its report (the PR-body completion, the issue comment, the close on
  success, the arc42 activity) instead of dying with an undefined-name error
  before any of its report work. The body keeps calling the plumbing by bare
  name — the change is in how the names are bound, not in the body's calls;
  the `ImportError` branch and its local fallback definitions are kept
  as-is (they are the fallback path task 2 pins), and the block keeps the
  shape the stage-contract harness extracts (it stays the step's `run: |`
  body beginning with `try:`).
  *(Fulfils AC-1 — scenario "The report step's plumbing is bound on a
  runner where the shared module imports", **new**: "the step's plumbing
  names are bound for the step's body" and "the step does not fail with an
  undefined-name error before any of its report work has run")*
  Proven by: **add**
  `tests/test_stage_contract.py::test_report_step_plumbing_is_bound_on_the_import_path`
  — the file's existing `_run_report_action` sandbox (a temp workspace, a

  wrapper writes before any report work is not produced); and the report
  completes on that path (the final PR body carries the final status; the
  issue comment is posted). No existing test covers the import path, so the
  proof is a new test.
  arc42 context: the report component (chapter 6's building-block row —

- [x] **Task 2 — keep the fallback plumbing effective and make the
  fallback-completed report equal the import path's.**
  The goal: where the shared module does not resolve from the runtime tree,
  the step's `ImportError` branch stays in force — the body runs on its
  local fallback definitions (the state dir, the state file, the log, the
  gh api, the branch push) and completes its report — the PR-body
  completion, the issue comment, the close on success, the arc42 activity —
  as on the import path: the two paths are behaviourally equivalent for the
  report's output (one ledger, one set of numbers on both surfaces). The
  fallback definitions themselves stay as they are — the standing
  stage-contract tests assert the report the forced-fallback run completes,
  and they keep passing unchanged against the step source task 1 modifies.
  *(Fulfils AC-2 — scenario "The report step's fallback plumbing stays
  effective where the shared module cannot import", **new**: "the step's
  body runs on its local fallback definitions" and "the step completes its
  report as on the import path")*
  Proven by: **add**
  `tests/test_stage_contract.py::test_report_fallback_plumbing_completes_the_report_as_the_import_path`
  — run the existing `_run_report_action` sandbox on both import
  resolutions (the import path task 1 makes work, and the forced-fallback
  path the standing tests use) and assert the two completed reports agree:
  the same final-status content on the PR-body surface and the same issue
  comment (the usage totals, the stage outcomes, the pointer vs.
  self-contained comment form, the close state). **Edit** the file's
  `_run_report_action` harness to parameterise the import resolution — its
  body today unconditionally scrubs the scripts dir from `sys.path` and
  pops the `common` module from `sys.modules` (the forced-fallback setup
  every standing test in the file relies on); the edit adds the parameter
  with the current forced-fallback behaviour as the default, so the
  standing tests keep passing unchanged — an unchanged older file next to
  the newly changed step is a contradiction the review stage would flag,
  and the standing tests' assertions (the "stays effective" half of the new
  scenario, and the changed file's standing scenarios) are the consistency
  guard.
  arc42 context: the deployment view (chapter 8 — "tags are immutable, so
  targets pinned to an older ref keep working"): a target pinned to a
  factory ref whose tree carries no resolvable shared module must still have
  stage 15 complete its report — the local fallback definitions are the
  mechanism that keeps those pinned targets working, and the import path
  (task 1) is the mechanism for a healthy runner. No contradiction with the
  arc42 set: the fallback extends the documented self-contained,
  pinned-refs-keep-working mechanism.
