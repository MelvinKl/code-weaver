# Issue #94 — A completed stage's work is committed and pushed to the AI branch; every completed implementation step likewise

## Summary

Make the AI branch's push a part of stage completion inside the stage
machinery, not a job-tail workflow step a terminated run never reaches: the
shared generation loop pushes the branch after each clean iteration (a
stage-completion push for the single-call stages, a push after each completed
step — before the next step starts — for the implement stage), the
dependency-upgrade workflow step pushes after its own commit, and the review
stage pushes at its completion point. The delta's two new scenarios and the
doc/count ripple (185 → 187 oracle scenarios) ride along, plus the
runtime-tree re-embed.

## Description

The requirement delta this plan covers (standing in-place shape — both
changed files existed at the run's baseline and changed in place, purely by
scenario addition, so the brownfield clause does not apply; a normal
implementation plan):

- **`requirements/implement.feature`** — one **new** scenario: "Every
  completed implementation step is committed and pushed" (a completed
  step's changes are committed on the AI branch → the stage pushes the AI
  branch before it starts the next step; a run terminated after that push
  keeps the completed step's work on the remote branch; a re-triggered run
  finds the step still marked done in the plan file).
- **`requirements/safety.feature`** — one **new** scenario: "A completed
  stage's work is committed and pushed to the AI branch" (a stage that has
  finished its work on the AI branch → when the run proceeds to the next
  stage, the stage's changes are committed to the AI branch and the branch
  is pushed; a run terminated after that stage loses none of the completed
  stage's work).

What the machinery does today, and the gap the delta closes:

- **Commits are already in-stage.** The shared generation loop commits
  after every clean generation call; the guard's repair commits its
  reverts; the review and gates fix loops commit each fix (and push per
  iteration); the report step commits its AI-activity section and pushes;
  the dependency-upgrade workflow step commits its footprint.
- **Pushes today ride job-tail workflow steps** (the "Push the AI branch"
  step last in each stage job — skipped whenever a job step fails) plus the
  in-script pushes above. So for the single-call stages (extract, plan) the
  work is committed in-stage but pushed only by the job-tail step: a run
  terminated between stage completion and that step loses the completed
  stage's work. For the **implement** stage the exposed window is long and
  load-bearing — the per-step loop runs one pi call per step (each under the
  360-minute call cap), and a run terminated mid-job has pushed nothing
  since the previous job: every completed step's commit, and the plan-file
  checkbox flips committed with them, sit on a dead runner's local branch,
  so a re-triggered run re-checks out a stale plan and would redo completed
  steps. The **dependency-upgrade** step commits but pushes only at
  job-tail — if the implement stage later fails, the job dies and the
  upgrade's committed work is lost.
- **The change:** push at stage completion, inside the stage machinery —
  the shared loop pushes after each clean iteration (and on the no-op exit
  path), the upgrade step pushes after its commit, the review stage pushes
  at its completion point (a no-op in the normal case, its fix iterations
  already pushing — the guarantee is explicit and uniform). The push fires
  only after the guard has passed, so a violating iteration is never
  pushed and the remote branch stays at the last completed clean state.
  Unchanged: the baseline job (its work is the branch cut, already pushed by
  its adjacent step; a re-trigger re-cuts idempotently), the pr job, the
  report step, the review/gates fix-loop pushes, and the jobs' existing
  job-tail push steps (now redundant no-ops for stage work, kept as the
  job's final sync — including the failed-job path the gates job keeps).
- **No extra mechanism** serves the implement scenario's last And line: the
  step's commit sweeps the working tree — the plan file's checkbox flip is
  re-allowed over the denied plans dir, so it rides in the same commit the
  push carries; a re-triggered run reuses the remote branch (resume
  semantics) and reads the step still done.
- **No prompt-template change:** the templates never instruct the model to
  commit or push — that work is the machinery's, before and after.

Consequences the plan must land with the code: the two new tests (and the
fake-git-model extension they assert on), the documented oracle counts
(185 → 187 scenarios, 16 files unchanged — the tree's current state), the
arc42 chapter 1/6/7/11 wording for the push guarantee, the README's count
lines and stage-8 line, and the factory-workflow runtime re-embed.

## Acceptance Criteria

Each mapped to the Gherkin scenario it fulfils (new = no existing scenario
covers it; ripple = an unchanged scenario whose obligation the delta
triggers):

1. `implement.feature::Every completed implementation step is committed and
   pushed` — **new**.
2. `safety.feature::A completed stage's work is committed and pushed to the
   AI branch` — **new**.
3. `requirement-extraction.feature::The documented oracle counts match the
   requirements tree` — **ripple** (the tree grows to 187 scenarios across
   the same 16 files; every documented count surface must read 187).
4. `implement.feature::The arc42 documentation is updated and complete` —
   **ripple** (chapters 6, 7 and 11 must record the push-at-completion
   guarantee and the implement stage's per-step push).
5. `implement.feature::The README is kept current` — **ripple** (the
   repository-layout and Requirements count lines; the stage-8 line gains
   the per-step commit-and-push wording).
6. `reuse-by-ref.feature::A published version is self-contained` —
   **ripple** (the runtime-tree changes of the steps below require the
   deterministic re-embed; a stale splice turns the byte-compare contract
   red before a release is tagged).

## Steps

- [x] **Make the push part of stage completion in the stage machinery.**
      **Goal and requirements.** The shared generation loop (the shared
      plumbing every generation stage script — extract, plan, implement —
      runs through) pushes the AI branch to the remote as part of the stage
      completing: after each clean iteration (the stage's changes committed,
      the guard passed) and on the no-op exit path, before the run proceeds
      — for the single-call stages that is the push at stage completion; for
      the implement stage, whose per-step loop runs one shared-loop call per
      step, that is a push after each completed step, before the next step
      starts. The push reuses the factory's sanitised push idiom (token
      rewritten out of the log, GIT_CONFIG hygiene) and resolves the branch
      name through the documented stage-value channel (the `AI_BRANCH` job
      env every stage job writes, with the `CW_`/trigger-state fallback);
      where the branch is unresolvable (an idle run) it skips with a log
      line rather than failing, while a push that actually fails fails the
      stage — its work would not be on the remote, and the next stage or a
      re-trigger would lose it. Alongside it: the workflow's
      dependency-upgrade step pushes the branch after committing its
      footprint (a completed stage's work must survive a later stage
      failing in the same job), and the review stage pushes the branch at
      its completion point. The push fires only after the guard has passed —
      a violating iteration is never pushed, the remote branch stays at the
      last completed clean state. The prompt templates are unchanged (the
      model is never told to commit or push — that is the machinery's), and
      so are the baseline job, the pr job, the report step, the review and
      gates fix-loop pushes, and the jobs' existing job-tail push steps
      (now redundant no-ops for stage work, kept as the job's final sync —
      including the failed-job path the gates job keeps). Fulfils: new
      `safety.feature::A completed stage's work is committed and pushed to
      the AI branch` (the extract and plan stages' work is committed
      in-stage today but pushed only by the job-tail step a terminated run
      never reaches — the stage-completion push closes that gap; the
      upgrade-step push closes it for the dependency-upgrade stage), and the
      mechanism half of new
      `implement.feature::Every completed implementation step is committed
      and pushed` (one shared-loop call per step, so the shared loop's
      clean-exit push is exactly "push the AI branch before it starts the
      next step", carrying the step's commit — which sweeps the working
      tree, the plan file's checkbox flip included).
      **Test that proves it.** Add a stage-sandbox test implementing the
      safety scenario — a single-call generation stage (the plan stage) run
      to clean completion in the suite's existing stage-sandbox idiom,
      asserting a push of the AI branch was recorded after the stage's
      commit and that the pushed tip is the commit carrying the stage's
      changed file; to make that assertable, extend the suite's shared
      in-test fake-git model so `push` invocations are recorded (they are
      silent no-ops today — the standing sandboxes' behaviour is unchanged,
      and the standing tests that run the shared loop and the guard stay
      green — an unchanged older file next to the newly changed behaviour is
      a contradiction the review stage will flag, and this edit keeps the
      sandbox suite consistent with the new behaviour). The new test's
      docstring cites
      `requirements/safety.feature::A completed stage's work is committed
      and pushed to the AI branch`.
      **arc42 context.** Chapter 7's stage flow (the push moves from the
      job-tail workflow step into the stage completion; the branch remains
      the documented cross-job channel), chapter 5's branch-hygiene bullet
      (it gains the push-at-completion guarantee), and chapter 6's
      shared-plumbing / extract / plan / review rows. No contradiction: the
      review and gates fix loops already push per iteration inside the stage
      scripts, and the report step already commits and pushes its own work —
      this extends an established idiom to the remaining completion points.
