# Issue #60 — The factory's reusable workflow names its own composite
actions by owner, repo and path; every published version is self-consistent
in its action references

**Summary**

The factory's reusable workflow (`.github/workflows/factory.yml`) references
its own composite actions by **relative path** (all ten own-action
`uses:` lines are `./.github/actions/<name>/`). In a *called* reusable
workflow the runner resolves a relative action path against the **calling
repo's checkout** — so the factory's own runs on this repo work (this tree
holds the actions), but a target consuming the documented pattern, whose
tree holds no copy of the factory's actions, crashes at the first
composite-action step ("Can't find 'action.yml'"). This change:

1. fully qualifies every own-action reference in the workflow (owner, repo,
   path — `MelvinKl/code-weaver/.github/actions/<name>@<ref>`), all pinned
   to one shared version ref;
2. makes the release flow rewrite those references to the tag it is about
   to create *before* it tags — every version the flow publishes from now
   is self-consistent: the workflow and its composite actions are one
   version, and a target's ref bump selects them as one version;
3. points the documented consumption (the README's example, this repo's own
   consumer workflow, and the arc42 surfaces that repeat it) at the first
   self-consistent published version, restoring the README/consumer
   lock-step the deployment view states.

**Description**

The changed requirements are a delta in `requirements/reuse-by-ref.feature`:
three **new** scenarios — "The factory's workflow names its own actions by
owner, repo and path", "The README's consumption pattern works on a target
repo", "A published version is self-consistent in its action references" —
and one **adjusted** scenario — "Composite actions are referenced by owner,
repo and path", whose And line moves from "the workflow's own steps
reference the factory's actions **by path** — pinned to that same ref" to
"the factory's own workflow steps reference its composite actions **by
owner, repo and path** — pinned to that same ref".

Two boundaries the plan works around, both grounded in the standing oracle
and the arc42 set:

- **Already-published tags are immutable.** Tags 1–4 carry the relative
  refs and cannot be re-cut: the standing scenario "Every published version
  is a stable ref" ("workflows pinned to an older ref keep working") and the
  release contract ("tags are immutable") forbid it. The self-consistency
  mechanism therefore governs the versions published from this change on;
  the documented consumption names the first self-consistent version, so
  the README's pattern is never a broken one, and older refs stay valid,
  stable refs (a target whose tree carries a copy of the actions keeps
  working against them).
- **The suite is red on main today** — `test_stage_contract.py::test_consumer_workflow_pins_owner_and_version_tag`
  still pins the retired semver ref shape (`vX.Y.Z`) while the versioning
  change moved the tag scheme to a single increasing number and the deployed
  consumer workflow pins `@1`. That failing test proves the standing
  scenario "The factory is invoked as a reusable workflow" — a scenario in
  the feature file *this run changes*, hence inside the review's verdict
  scope — so this run must align it with the standing oracle ("Every
  published version is a stable ref": "its tag is a single increasing
  version number") or the review cannot pass.

**Acceptance Criteria**

- **AC-1** — every step of the factory's reusable workflow that invokes one
  of the factory's own composite actions names it by the factory's owner,
  repo and path, and no own-action reference in the workflow is a relative
  path (a relative path in a called reusable workflow resolves against the
  calling repo's checkout).
  *(Scenario "The factory's workflow names its own actions by owner, repo
  and path" — **new**)*
- **AC-2** — a target whose consumer workflow is written exactly as the
  README documents it, and whose tree holds no copy of the factory's
  composite actions, runs every stage job's composite-action step against
  the factory's own action definitions (fetched from the factory repo at
  the pinned ref); no step fails with a missing action file under the
  target's own checkout, and the run does not crash at the first stage that
  invokes a composite action.
  *(Scenario "The README's consumption pattern works on a target repo" —
  **new**)*
- **AC-3** — for every version ref the release flow publishes from this
  change on, the workflow at that ref references all of its own composite
  actions at that same version ref — a target's ref bump selects the
  workflow and its actions as one version.
  *(Scenario "A published version is self-consistent in its action
  references" — **new**)*
- **AC-4** — the consumer's `uses:` line names the factory by owner, repo,
  path and ref, and the factory's own workflow steps reference its
  composite actions by owner, repo and path — pinned to that same ref (the
  version ref the consumer pins, materialized at that tag by the release
  flow's pre-tag rewrite).
  *(Scenario "Composite actions are referenced by owner, repo and path" —
  **adjusted**; the And step's expected outcome changes from relative
  "by path" references to fully-qualified "by owner, repo and path" ones)*
