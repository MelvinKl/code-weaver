# Issue #23 — The setup-pi stage installs and configures pi for the run

**Summary**

The pi harness stops being a **pre-requisite of the runner environment** and
becomes **provided for the run**. Stage 2 (`setup-pi`) flips from
*verify-only* (pi present → configuration found → backend reachable → model
in set → smoke check; "the factory never installs or re-configures pi") to
*install and configure for the run*: it installs pi so every later pi
invocation in the run uses that installed copy, and it materialises the
run's harness — the model configuration, the additional packages, the MCP
configuration, the extension's environment variables — from per-run
providers (a GitHub secret **or** the repo file for each element) into the
agent subdirectory (`~/.pi/agent/`, or `PI_CODING_AGENT_DIR`) the run's pi
invocations resolve. The harness providers ride the reusable workflow's
`secrets:` block (never `with:` inputs or committed files), the workflow and
consumer-workflow surfaces are wired accordingly, and the README + arc42
rewrite their "pre-installed & pre-configured pi" statements to the new
contract — listing the providers — while the stale documented oracle counts
(135) are brought to the tree's actual figure (15 files, 149 scenarios after
this run's delta).
