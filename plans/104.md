# Issue #104 — A factory run on a target repo different from the factory's own repo crashed in its first job: the actions/checkout fetch of the runtime tree into the runner's temp dir is refused for a different repo; make the first job's fetch work for that shape, and pin the trigger's artifact carrying the stashed tree to every stage job

## Summary

A factory run on a target repo *different* from the factory's own repo crashed in
its first job. The trigger job's runtime-tree fetch step is an `actions/checkout`
— a checkout of the factory repo at the called ref into the runner's temp dir
(`$RUNNER_TEMP/cw/stash`), a path **outside the job's workspace**. The checkout
action refuses a different-repo checkout to a path outside the workspace
("Repository path ... is not under ..."), while the same step passes in the
factory's own repo (the dogfood), where the checked-out repo is the triggered
repo itself. The empty stash starved the trigger's artifact (its upload runs
`always()` with the hidden-file opt-in, but there was no tree in it to
upload), and every later stage job died on a missing stashed runtime file.

The delta adds two scenarios to `requirements/reuse-by-ref.feature` that pin
the fix:

1. **The runtime tree fetch succeeds on a target repo different from the
   factory's own repo** — the first job fetches the called version's runtime
   tree from the factory repo at the called ref into the runner's temp dir,
   *without the fetch failing*; the materialised tree is the called
   version's — the tree of the ref the consumer's `uses:` line selects.
2. **The trigger's artifact carries the stashed runtime tree to every stage
   job** — the artifact contains the stashed tree, including the hidden
   directory the stage scripts live under; every later stage job restores the
   tree from the trigger's artifact before its first checkout; and no stage
   job of the run dies on a missing stashed runtime file.

The plan: (1) flip the trigger job's fetch from a checkout-action step to a
plain `run:` step that `git clone`s the called repo at the called ref into the
stash — anonymous (a public-repo fetch; the target-scoped `GH_TOKEN` contract
untouched), riding the runtime-resolved called-repo/called-ref (no literals in
the file; the recovery step unchanged), the curated curation and the
repo-relative layout kept — one uniform mechanism serving every consumption
shape; (2) add the oracle join for the new scenario onto the artifact relay
that is already shaped in the file (the upload with its hidden-file opt-in,
the per-job download before the first checkout, the stage steps'
precise-failure guards); (3) reconcile the stated oracle counts (198 → 200)
and flip the one documented surface that names the old mechanism. The one-ref
architecture is unchanged — the consumer's `uses:` line stays the only pin.

## Description

The delta is a **standing in-place change** to the existing
`requirements/reuse-by-ref.feature` (the file predates the run's baseline —
the diff modifies it, it creates nothing; the brownfield clause does not
apply). It **adds two scenarios** (both tagged `@reuse @issue-104`, at the
file's end, plus the header comment naming the crash and its cause) and
**rewords no existing scenario**:

- **Added (new):** `The runtime tree fetch succeeds on a target repo
  different from the factory's own repo` · `The trigger's artifact carries the
  stashed runtime tree to every stage job`.

Net, the oracle's tree grows from **198 to 200 scenarios** (16 files
unchanged; both additions sit in `reuse-by-ref.feature`), while every
documented surface still states 198 — the adjacent existing scenario
`requirement-extraction.feature::The documented oracle counts match the
requirements tree` is red until step 3 reconciles the stated counts.

**The root cause (the delta's header comment, confirmed against the current
file).** The trigger job's fetch step is:

```yaml
uses: actions/checkout@v7
with:
  repository: ${{ steps.called-version.outputs.called-repo }}
  ref: ${{ steps.called-version.outputs.called-ref }}
  path: ${{ runner.temp }}/cw/stash
  token: ""
  sparse-checkout: |
    /.github/scripts
    /.github/actions
    /pi-prompts
```

The checkout action admits a `path` outside the job's workspace only when the
checked-out repo *is* the triggered repo itself. In the dogfood the recovery
resolves the called repo to the triggered repo (the factory project itself) —
the same repo — so the temp-dir path is admitted and the step passes. On any
*other* target repo the called repo (`MelvinKl/code-weaver`) is a *different*
repo — the action refuses the out-of-workspace path. The stash stays empty;
the trigger's `cw-trigger` upload (which runs `always()` and opts into hidden
files) uploads no tree; every later stage job's first step restores nothing;
and every stage job dies at its stage step's guard on the missing stashed
runtime file. The stash *must* sit in the runner's temp dir (a checkout
replaces the workspace; only `RUNNER_TEMP` survives every later checkout —
the pinned "before the first checkout" boundary), so the fix is not to move
the fetch inside the workspace; the fix is the fetch's mechanism.

**The design this plan scopes.**

- **The fetch becomes a plain `run:` step that `git clone`s the called repo
  at the called ref into `$RUNNER_TEMP/cw/stash`** — anonymous (no token;
  the factory repo is public, and the documented `GH_TOKEN` contract — a
  token scoped to the target repo — still does not ride the fetch), riding
  the runtime-resolved `called-repo`/`called-ref` outputs the unchanged
  `called-version` recovery step emits (no repo/ref literal anywhere in the
  file), with the curated curation surviving the flip (the
  `.github/scripts`, `.github/actions`, `pi-prompts` prefixes,
  repo-relative under the stash — the stage scripts' `__file__`-relative
  resolution and the publication gate's canonical file set are unchanged). A
  clone lands the tree of the called ref's commit — the same ref that
  selected the workflow file — so "one ref, one version" survives the flip:
  the file GitHub fetched and the tree the first job fetches are still the
  two halves of the tag's commit, and the consumer's `uses:` line stays the
  only pin.
- **One uniform mechanism serves every consumption shape.** An external
  target's owner-qualified recovery resolves the factory repo at the version
  tag — a public repo an anonymous clone reads (the target repo's privacy is
  irrelevant: the fetch source is never the target). The dogfood's recovery
  resolves the factory's *own* public repo at its pinned tag — also a plain
  clone of a public repo; the dogfood scenario's "never a clone of the
  factory repo at a **second** ref" stays true, because the clone rides the
  **called** ref (the only ref), not a relayed second one. The legacy
  relative-`uses:` form (the triggering repo at the run's base ref) resolves
  through the unchanged recovery and works under the same uniform clone.
- **The artifact side is already shaped in the file; the new scenario pins
  it.** The trigger's `cw-trigger` upload (`if: always()`,
  `path: ${{ runner.temp }}/cw`, `include-hidden-files: true` — the hidden
  `.github/` directory under the stash is the half the artifact API would
  otherwise drop), every later stage job's first step (the download of the
  trigger's artifact into `$RUNNER_TEMP/cw` before its first checkout), and
  each stage step's precise-failure guard on a missing stashed script (the
  named file, an explicit `::error::`, not an opaque crash) — with the fetch
  succeeding and the upload carrying the tree, the chain is complete and no
  stage job dies on a missing file. Step 2 adds the test join for the new
  scenario; it changes nothing in the workflow file.
- **The old pin the new scenario invalidates.** Two suite tests pin the
  fetch's old form — `test_no_run_fetches_the_factory_repo` ("no raw
  `git clone` in the file; the fetch is an `actions/checkout` step whose
  `repository:` input rides the runtime-resolved `called-repo`") and
  `test_factory_file_carries_its_runtime_tree_embedded` (the fetch step's
  `ref:`/`path:` action-input regexes) — both citing the *unchanged* scenario
  `A published version is self-contained`. That pin is exactly the mechanism
  the new scenario invalidates (the checkout action structurally refuses the
  different-repo shape), so both tests flip in step 1 — the cited scenario's
  content stays true (one ref selects the whole version; the file stores no
  binary payload); what flips is the mechanism half, and the docstrings
  re-ground it, naming the new scenario. An unchanged older file next to the
  newly changed one is a contradiction the review stage will flag.
- **One documented surface names the old mechanism.** The README's "Why the
  consumer pins once" paragraph ("the fetch is an anonymous **checkout** that
  does not ride the target-scoped `GH_TOKEN`") is the only doc surface that
  names the fetch's mechanism — it flips to the anonymous-clone form in step
  1, and the in-file header comment of `factory.yml` flips in the same edit.
  The arc42 chapters describe the fetch only conceptually (the chapter 6
  reusable-workflow line and the chapter 8 paragraphs: "stage 1 fetches the
  called version's runtime tree at the called ref into `$RUNNER_TEMP` before
  the first checkout; the trigger's artifact carries it to every later stage
  job's first step — that upload opts into hidden files…") — no chapter names
  the checkout action, so nothing in the arc42 set contradicts the flip.
- **What stays unchanged:** the `called-version` recovery step (the consumer
  workflow read over the GitHub API at the run's base ref; the
  owner-qualified and relative forms); the verify step (the canonical marker
  files in the stash, the precise failure on a short fetch); the `rm -rf` of
  the stash ahead of the fetch; the trigger's upload step; every later job's
  download-and-restore; the stage steps' missing-file guards; the consumer
  workflow's shape; the release flow and its publication gate; the file's
  self-contained / plain-text / at-most-500kb shape.

## Acceptance Criteria

- **AC1** — `requirements/reuse-by-ref.feature::The runtime tree fetch
  succeeds on a target repo different from the factory's own repo` (**new** —
  no baseline scenario covers it): given a target repo that is different from
  the factory's own repo, whose consumer workflow invokes the factory's
  workflow at a version tag, when a factory run on that target repo reaches
  its first job, then the first job fetches the called version's runtime tree
  from the factory repo at the called ref into the runner's temp dir, the
  fetch completes without failing, and the materialised runtime tree is the
  called version's — the tree of the ref the consumer's `uses:` line selects.
- **AC2** — `requirements/reuse-by-ref.feature::The trigger's artifact
  carries the stashed runtime tree to every stage job` (**new** — no baseline
  scenario covers it): given a factory run on a target repo that is different
  from the factory's own repo, whose first job materialised the called
  version's runtime tree into the runner's temp dir, when the trigger job
  uploads its state artifact, then the artifact contains the stashed runtime
  tree — including the hidden directory the stage scripts live under — every
  later stage job restores the tree from the trigger's artifact before its
  first checkout, and no stage job of the run dies on a missing stashed
  runtime file.
- **AC3** — `requirements/requirement-extraction.feature::The documented
  oracle counts match the requirements tree` (**adjacent existing scenario,
  invalidated as a side effect of this delta** — its file is unchanged, but
  its expectation is): the stated scenario count on every doc surface (the
  README's layout line and Requirements section, chapter 1's two mentions,
  chapter 6's oracle row, chapter 11's "Oracle" entry) matches the tree the
  delta left behind — **200** scenarios (the 16-file count is unchanged).
