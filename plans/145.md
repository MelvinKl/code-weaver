# Issue #145 — a new optional factory stage (the update stage) between requirement-extraction and planning: it updates all requirements to the newest version unless a Gherkin requirement prohibits it; the AUTO_UPDATE setting (true by default, configurable per target) turns it off; the bug-labelled run's flow is re-seated through it; the grown oracle's stated counts are reconciled

## Summary

The delta introduces the **update stage** — an optional stage that sits in
the pipeline after the requirement-extraction stage and updates all
requirements to the newest version unless prohibited by a Gherkin
requirement — together with the **`AUTO_UPDATE` setting** that turns it
off (default `true`), and re-seats the bug-labelled run's flow: a
bug-labelled run that skips the extraction stage now **proceeds to the
update stage and then to the planning stage** (the update stage sits
between the two). Three requirement files changed: a new topic file
`requirements/requirements-update.feature` (four scenarios — no existing
file covered the update stage), one added scenario in
`requirements/configuration.feature` (the setting's configurability,
shaped on the adjacent dependency-upgrade scenario), and one changed
line in `requirements/requirement-extraction.feature` (the last Then of
"A bug-labelled run skips the extraction stage"). This is a **full
implementation plan** — factory code, oracle tests and documented
surfaces — not a brownfield test-adjustment plan: two of the three
changed files are changed existing files, so the delta is the standing
in-place shape and the brownfield clause does not apply.

## Description

**The delta's shape.** Standing in-place: `requirements-update.feature`
is new; `configuration.feature` and `requirement-extraction.feature` are
modified in place. The oracle's tree grows from **16 files / 174
scenarios to 17 files / 179 scenarios** (one scenario added in
`configuration.feature`, four in the new file, zero net in
`requirement-extraction.feature` — its change is a line inside an
existing scenario).

**What the delta says.**

- **New file `requirements/requirements-update.feature`** — four
  scenarios for the new stage: (1) the update stage runs between the
  requirement-extraction and the planning stages (AUTO_UPDATE on);
  (2) a target that leaves AUTO_UPDATE undeclared resolves it to its
  true default and its pipeline runs the update stage; (3) the stage
  updates **all** requirements to the newest version; (4) a Gherkin
  requirement can prohibit the update of a requirement — the prohibited
  one is left at its current version, the unprohibited ones are updated.
- **`configuration.feature`** adds **The AUTO_UPDATE setting is
  configurable**: default `true`; a target turns it off via its workflow
  inputs; the run's pipeline then runs without the update stage, and the
  run's stages, pull request and final status report are unchanged by
  the stage's absence.
- **`requirement-extraction.feature`** changes the last Then of **A
  bug-labelled run skips the extraction stage** from "And the run
  proceeds directly to the planning stage" to "And the run proceeds to
  the update stage and then to the planning stage".

**Consequences the delta forces on the code and the documented
surfaces** (none of these is a scenario of the delta; each is pinned by
the standing oracle or the arc42 set):

- The documented oracle counts go stale: the README (repository-layout
  line and Requirements section), chapter 1 (two places), the chapter 6
  building-block table and the chapter 11 glossary entry all still state
  **16 files, 174 scenarios** while the tree holds 17 / 179 — the
  standing scenario `The documented oracle counts match the
  requirements tree` is red until step 4 reconciles the stated counts
  (`tests/test_oracle_counts.py` is the suite's currently failing test).
- The documented flow wording contradicts the adjusted scenario: chapter
  6's extract-stage line and the README's item 4 say the bug-labelled
  run "proceeds directly to the planning stage" (chapter 6 pinning
  "the 15-stage / 9-job shape is unchanged — the skip is a recorded
  outcome inside the existing job, not a new stage or job"), and
  chapter 7's stage-flow paragraph says the bug-labelled run "proceeds
  to a plan built from the issue itself". Step 2 lands the change; step
  4 rewords the surfaces.
- The stage's pi call needs its own prompt template: chapter 6's
  shared-plumbing line pins "the `pi-prompts/` template count stays
  five, one per stage". The new stage moves the set to six — the
  "one per stage" shape holds — and the canonical runtime file list the
  release flow's publication gate checks must gain the new template so a
  tagged commit's tree carries it.

**The design this plan scopes (grounded in the arc42 set).** The update
stage lands as an **inlined step in the existing `plan` job** — after
that job's AI-branch checkout and before the plan stage step and its
stage-baseline recording. That is the documented dependency-upgrade
idiom (chapter 5: "The stage is an inlined step in the existing
`implement` job … after its checkout of the AI branch and before the
stage step and its stage-baseline recording, so the upgrade's footprint
is never counted as the stage's work by the guard … it is inlined
workflow text, not a new component — no new job is added, the
15-stage / 9-job pipeline count stays, and the self-contained shape is
preserved"). The consequences that idiom buys: the 15-stage / 9-job
shape and the five stage jobs that make pi calls (extract, plan,
implement, review, pr — chapter 5/6, all unchanged), the step's pi call
rides the plan job's documented `job-timeout`, and the plan check's
baseline (recorded by the plan stage, after the step) never feeds on the
update's footprint. The `AUTO_UPDATE` setting rides the documented
settings channel (chapter 3's `CW_<name>` step-env idiom): the input
declared on the reusable workflow's input surface (string, optional,
default `true`), recorded by the trigger as a state file beside its
recorded run state, relayed by every stage job's Read-trigger-state step
like the other trigger-state keys, and named in the trigger's
resolved-configuration record (workflow log, never committed). A run
whose extraction stopped with the `no-delta-stop` flag — already relayed
to the plan job and already checked by the plan stage before its own
work — gets the step no-op'ing on that flag, so the documented
clean-stop outcome (no work, the PR and the report as the scenarios
read) is undisturbed. "The newest version" is the documented
in-place-update idiom generalised (chapter 10: "a delta that supersedes
a standing scenario updates that scenario in place (the oracle is the
single source of truth)"): the stage reconciles every scenario with the
project's current state; a requirement already at its newest version —
including the ones this run's extraction just derived — is left
untouched, so the update's footprint never disturbs the run's delta the
plan stage covers.

## Acceptance Criteria

1. **The `AUTO_UPDATE` setting is configurable.** The reusable
   workflow declares `auto-update` — a string input, optional (an older
   consumer's `with:` block stays schema-valid), default `true` (the
   scenario pins that literal); a target that turns it off via its
   workflow inputs makes the run's pipeline run without the update
   stage, and the run's stages, pull request and final status report
   are unchanged by the stage's absence.
   — fulfils `configuration.feature::The AUTO_UPDATE setting is
   configurable` (**new**).
2. **An undeclared `AUTO_UPDATE` resolves to its true default.** A
   target that leaves the input undeclared resolves it to `true`
   through the documented settings channel (the trigger's state file,
   the per-job env relay, the resolved-configuration record), and the
   run's pipeline runs the update stage.
   — fulfils `requirements-update.feature::A target that leaves
   AUTO_UPDATE undeclared runs with the update stage` (**new**).
3. **The update stage sits between the requirement-extraction and the
   planning stages.** With AUTO_UPDATE on it runs after the pipeline has
   passed the requirement-extraction stage and before the planning
   stage — as an inlined step in the existing `plan` job (after the
   AI-branch checkout, before the plan stage step and its
   stage-baseline recording); no new job, the 15-stage / 9-job count and
   the five pi-calling stage jobs unchanged.
   — fulfils `requirements-update.feature::The update stage runs between
   the requirement-extraction and the planning stages` (**new**).
4. **The update stage updates all requirements to the newest version.**
   When it runs, every requirement in the oracle is reconciled to its
   newest version — a scenario that no longer holds against the
   project's current state is updated in place, a requirement already at
   its newest version is left untouched, a changed feature file must
   still parse with Cucumber's official parser, the work is committed to
   the AI branch and pushed, and the stage records its outcome on the
   stage-summary channel.
   — fulfils `requirements-update.feature::The update stage updates all
   requirements to the newest version` (**new**).
5. **A Gherkin requirement can prohibit the update of a requirement.**
   A Gherkin requirement that prohibits a requirement from being updated
   leaves that requirement at its current version; the requirements no
   Gherkin requirement prohibits are updated to the newest version.
   — fulfils `requirements-update.feature::A Gherkin requirement can
   prohibit the update of a requirement` (**new**).
6. **The bug-labelled flow re-seats through the update stage.** A run
   for an issue that carries the trigger label and the bug label skips
   the extraction stage (no pi call, no requirement file written, the
   requirement check passes with no requirement file changed) and then
   proceeds to the update stage and then to the planning stage — the
   former "proceeds directly to the planning stage" outcome is
   superseded; a bug-labelled run whose extraction stopped with the
   `no-delta-stop` flag keeps its documented clean-stop outcome (the
   step no-ops on the flag).
   — fulfils `requirement-extraction.feature::A bug-labelled run skips
   the extraction stage` (**adjusted** — its last Then changed).
7. **The documented oracle counts match the requirements tree.** Every
   doc surface that states the oracle's counts states **17 files, 179
   scenarios** — matching the tree the delta grew — and a surface that
   stated the old figures is reconciled.
   — fulfils `requirement-extraction.feature::The documented oracle
   counts match the requirements tree` (scenario unchanged; its input
   tree changed, so the stated counts must follow).
