# Issue #109 — fastmode: a configurable workflow input below which the implement stage works the plan's steps in a single iteration

## Summary

The delta adds a configurable workflow input, the **fastmode threshold**
(default `5` steps), and branches the implement stage on it: a plan whose
step count is **at or above** the threshold keeps the standing one-step-at-a-
time behaviour; a plan **below** it is worked in a single iteration — every
open step in one pi call, all marked done, no further per-step iteration. The
plan stage's ticket-style convention gains the same dual-mode clause, and the
arc42 set, the README and the stated oracle counts are brought in line (the
delta grows the oracle 170 → 172 scenarios).

## Description

The delta is a **standing in-place change**: all three changed requirement
files predate the run's baseline (the diff modifies them; it creates nothing),
so the brownfield clause does not apply and the standing instructions govern:

- **`requirements/configuration.feature`** — **adds one scenario** (new):
  `The fastmode threshold is a configurable workflow input` (the default is
  5 steps; a target's value is what the implement stage compares the plan's
  step count against; an undeclared input keeps the default of 5). Every other
  scenario in the file is unchanged.
- **`requirements/implement.feature`** — **adds one scenario** (new): `A plan
  below the fastmode threshold is implemented in a single iteration`;
  **amends one existing scenario**: `The implementation works the next open
  step and marks it done` gains the Given `the plan's step count is at or
  above the fastmode threshold` (its Then/And — work exactly one open step,
  the first from the top, mark it done — is unchanged); and the feature's
  header comment and purpose line are reworded to carry the dual mode.
- **`requirements/plan.feature`** — **amends one existing scenario**: `The
  plan is written in Jira ticket style` — its checklist And line now reads
  "…so the implementation works it one step at a time — or all steps in a
  single iteration where the plan is below the fastmode threshold" (the
  Jira-issue structure half is unchanged). No scenario is added.

Net: the oracle tree grows from **170 to 172 scenarios** (16 files, unchanged
— both additions sit in existing topic files). Until step 4 flips the stated
counts, the adjacent scenario
`requirement-extraction.feature::The documented oracle counts match the
requirements tree` is red (every doc surface still states 170).

**Undocumented surfaces this plan must say so about (hard rule 2):**
"fastmode" appears **nowhere** in the current arc42 set or the README — the
delta introduces the concept; step 4 is what documents it, and steps 1–2 plan
around the documented sibling-input pattern (the `pi-timeout` / `max-loops` /
`job-timeout` input machinery, chapters 3–7). Chapter 6 documents the test
*categories* (validator unit, stream-capture, trigger-contract,
stage-contract, release-contract tests), not the individual test files — this
plan therefore names the test files the tree actually holds and locates every
test by the documented docstring-citation form
`<feature file>::<scenario name>`.

  the reusable workflow declares a `fastmode-threshold` input whose default is
