# Issue #97 — The pi call time cap joins the configurable surface (`pi-timeout`)

## Summary

Make the factory's per-call pi time cap a first-class per-target setting: declare a
`pi-timeout` input on the reusable workflow (string, default `"21600"` — today's
360-minute cap), relay it to the stage jobs through the documented `CW_` job-env
idiom, have the stage code resolve it as `INPUT_PI_TIMEOUT` → `CW_PI_TIMEOUT` → the
21600-second code default, record the resolved value in the trigger's
resolved-configuration record, clamp any declared value to the stage jobs'
job-level `timeout-minutes` backstop (a factory-side property no input sets) and
record the exceedance, and keep the arc42 set and README current — including the
stated oracle counts the delta grows from 187 to 192 scenarios.

## Description

The delta is a standing in-place change to the existing
`requirements/configuration.feature` (the file predates the run's baseline; the
brownfield clause does not apply): five new scenarios, added between the loop-cap
scenarios and the dependency-upgrade scenario, all about the pi call time cap:

1. `The pi call time cap is a configurable workflow input`
2. `The pi call cap rides the job-env relay like every other setting`
3. `The resolved pi call cap rides the resolved-configuration record`
4. `A declared cap longer than the job's timeout backstop is not honoured`
5. `The job's timeout backstop is a factory-side property`

Current state of the machinery (the gap the steps close):

- The cap exists only as a hard-coded `21600` (360-minute) default on the shared
  pi-call plumbing (`common.pi_invoke`, and `stages.pi_stage`, whose comment already
  promises "overridable per call via CW_PI_TIMEOUT" — the code never reads the
  env). Every pi call in the pipeline (the stages' generation calls, the guard's
  repair call, the PR-body call) runs that one constant.
- The reusable workflow declares no `pi-timeout` input; the trigger's
  resolved-configuration log block records runner, model, label, branch, dirs,
  `max-loops`, `dependency-install` and `dependency-upgrade` — not the pi cap.
- The `pr` job's inlined PR-body call site carries its own divergent fallback
  (`int(_cw_in_opt("timeout") or 1800)` — a 30-minute local default, an option name
  no input declares), so that call does not ride the 360-minute cap.
- Only five of the nine stage jobs declare a job-level `timeout-minutes` backstop
  (`480`); the rest ride the runner's default, and no job's backstop is known to
  the stage code. The arc42 set does not name the job timeout backstop anywhere —
  step 4 adds that statement to the chapters (undocumented today; planned around,
  per the planning rules).
- The delta grows the requirements tree to 192 scenarios (16 files) while the
  documented surfaces still state 187 — the adjacent existing scenario
  `requirement-extraction "The documented oracle counts match the requirements
  tree"` goes red until step 6 updates the stated counts. The suite gates at the
  review stage, so that single test may sit red between steps and is turned green
  by step 6; no other older test's expectation changes.

The consumer workflow stays short and stable: a new optional input means a
consumer that leaves it undeclared runs unchanged (the 360-minute cap), and an
older consumer's `with:` block stays schema-valid.

## Acceptance Criteria

- **AC1** — `requirements/configuration.feature::The pi call time cap is a
  configurable workflow input` (new): the reusable workflow declares `PI_TIMEOUT`
  as a string input defaulting to `"21600"`; a target's value governs every pi
  invocation in the pipeline; an undeclared consumer keeps the current
  360-minute cap.
- **AC2** — `requirements/configuration.feature::The pi call cap rides the
  job-env relay like every other setting` (new): each stage job's env carries
  `CW_PI_TIMEOUT` with the declared value; the stage code resolves the cap as
  `INPUT_PI_TIMEOUT`, then `CW_PI_TIMEOUT`, then the 21600 default; a value set
  at the `CW_PI_TIMEOUT` link caps the run's pi calls.
- **AC3** — `requirements/configuration.feature::The resolved pi call cap rides
  the resolved-configuration record` (new): the trigger's resolved-configuration
  record lists the resolved cap (declared or default) with the rest of the
  resolved configuration, in the workflow log, never committed to the repo.
- **AC4** — `requirements/configuration.feature::A declared cap longer than the
  job's timeout backstop is not honoured` (new): a declared cap exceeding the
  stage job's job-level `timeout-minutes` backstop is clamped to that backstop;
  the run records that the declared cap exceeds the backstop.
- **AC5** — `requirements/configuration.feature::The job's timeout backstop is a
  factory-side property` (new): the backstop is declared in the factory's own
  workflow file; no input of the reusable workflow sets it.
- **AC6** — `requirements/requirement-extraction.feature::The documented oracle
  counts match the requirements tree` (adjusted by this delta: the stated
  scenario count changes from 187 to 192; the file count stays 16) — the stated
  counts on the doc surfaces equal the tree the delta left behind.

## Steps

- [x] **1. Declare the `pi-timeout` input on the reusable workflow's input
      surface**
  - *Goal (AC1, new requirement):* the factory's reusable workflow declares
    `pi-timeout` — a string input, optional (an older consumer's `with:` block
    stays schema-valid), default `"21600"` — following the existing
    `max-loops`/`dependency-upgrade` input pattern, so the cap becomes one of
    the settings a target overrides per repo through the `with:` block. A
    consumer that leaves it undeclared resolves the current 360-minute cap, so
    such a run is unchanged. The consumer workflow gains no line.
  - *Test (add):* a configuration-surface test in `tests/test_stage_contract.py`
    in the shape of `test_loop_cap_defaults_match_oracle` /
    `test_dependency_upgrade_setting_is_configurable`: the workflow file declares
    `pi-timeout` as an optional string input with default `"21600"`, and the
    README's Inputs table carries the row. Docstring cites
    `requirements/configuration.feature::The pi call time cap is a configurable
    workflow input`.
  - *arc42 context:* the reusable workflow's input surface and the README's
    Inputs table are documented surfaces (chapters 3, 4, 6). The value is a
    number of seconds — project configuration riding the input channel, never a
    secret, so the "secrets are never plain inputs" constraint is untouched. No
    contradiction with the arc42.

- [x] **2. Relay the value to the stage jobs and make the stage code resolve the
      cap through the documented chain**
  - *Goal (AC2 new, AC1's runtime half new):* every stage job relays the
    declared value as `CW_PI_TIMEOUT` in its job env (the documented
    `CW_<name>` step-env idiom), and the shared pi-call plumbing resolves each
    call's time cap as `INPUT_PI_TIMEOUT` → `CW_PI_TIMEOUT` → the 21600
    code default — closing the gap where `stages.pi_stage` promises the
    override in a comment but never reads the env. Every pi invocation in the
    pipeline rides that one resolution: the stages' generation calls, the
    guard's repair call, the `pr` job's PR-body call (whose inlined site today
    falls back to its own private 30-minute `1800` default — it must resolve
    `pi-timeout` through the shared chain instead), and the setup-pi stage's
    smoke check (its short probe budget is kept, and where the resolved cap is
    shorter the probe runs under the target's value, so "every pi invocation"
    holds). A value set at the `CW_PI_TIMEOUT` link caps the run's pi calls.
  - *Test (add):* a stage-contract test in the suite's established sandbox idiom
    (a fake job env driving the stage scripts / shared plumbing, as the
    guard-repair and loop tests already do): with `CW_PI_TIMEOUT` set, the pi
    subprocess call runs under that timeout; with neither env set, it resolves
    to the 21600-second default — plus a workflow-file assertion that each
    stage job's env relays `CW_PI_TIMEOUT` from the input. Docstring cites
    `requirements/configuration.feature::The pi call cap rides the job-env relay
    like every other setting` (and, for the undeclared-consumer half,
    `...::The pi call time cap is a configurable workflow input`).
  - *arc42 context:* the `CW_<name>` relay and the three-link resolution
    (`INPUT_*` → `CW_*` → the trigger state files) are pinned in chapter 3
    (composite-action input binding is unreliable on this runner build); the
    single shared pi-call plumbing is the chapter 6 component every stage call
    goes through. This step implements the override the loop machinery's own
    comment already promises — no new channel. The commit that changes the
    runtime tree re-runs the release pipeline's embed (`make embed`) in the
    same commit: the embedded-tree contract test
    (`tests/test_embedded_runtime.py::test_factory_file_carries_its_runtime_tree_embedded`)
    fails while the workflow file's payload is stale.

- [x] **3. Record the resolved pi call cap in the resolved-configuration record**
  - *Goal (AC3, new requirement):* the trigger stage's resolved-configuration
    record — the workflow-log block the trigger tees into its state file that
    rides the trigger's artifact — lists the run's resolved pi call cap with the
    rest of the resolved configuration: the declared value where a target
    declared one, the 21600 default where the input is undeclared. The record
    stays in the workflow log (and the run's artifacts), never committed to the
    repo.
  - *Test (add):* a resolved-configuration test in
    `tests/test_dependency_install_contract.py`'s existing trigger-block idiom
    (parse the trigger's `{ … } | tee` group between its heading and its close):
    the block carries a line naming the resolved pi call cap in both branches —
    a declared value and the default. Docstring cites
    `requirements/configuration.feature::The resolved pi call cap rides the
    resolved-configuration record`. The block's existing lines (max-loops,
    dependency-install, dependency-upgrade) stay asserted green by their
    current tests — the new line is added inside the same group.
  - *arc42 context:* "State rides artifacts, never the tree" and the audit
    surface of the existing "Settings flow from workflow inputs to stage env"
    scenario (chapter 5) already pin the record's location and its
    never-committed property; this step extends the existing record with one
    entry rather than creating a new one. No contradiction.

- [x] **4. Make the job-level timeout backstop an explicit, uniform
      factory-side property**
  - *Goal (AC5, new requirement):* every stage job in the factory's own workflow
    file declares its job-level `timeout-minutes` backstop (today five of the
    nine jobs declare `480`; the rest ride the runner's default), and the stage
    code knows that same value through the shared plumbing — so the backstop is
    declared in the factory's own workflow file, and no input of the reusable
    workflow sets it (the input surface stays closed; the backstop is a safety
    property of the factory, not a target setting).
  - *Test (add):* a workflow-file test (line-based read, the suite's
    stdlib-only idiom): each stage job in `factory.yml` declares a job-level
    `timeout-minutes`, the reusable workflow's input surface contains no entry
    that sets a job timeout, and the value the stage code resolves as the
    backstop matches the file's value. Docstring cites
    `requirements/configuration.feature::The job's timeout backstop is a
    factory-side property`.
  - *arc42 context (undocumented — planned around):* no arc42 chapter names the
    job timeout backstop; the `timeout-minutes` entries are a workflow-file fact
    the docs never state. This step therefore also plants the one-line
    statement that the stage jobs run under a factory-side job-timeout backstop
    that no input sets, in the chapters that describe the jobs and their loop
    machinery (chapter 5's bounded-loops bullet and the chapter 6 job table) —
    the implement stage's standing duty to keep the arc42 set complete. Where
    the step touches the runtime tree, the same-commit `make embed` rule of step
    2 applies.

- [x] **5. Clamp a declared cap to the job's backstop and record the
      exceedance**
  - *Goal (AC4, new requirement):* where a target declares a `PI_TIMEOUT` longer
    than its stage job's timeout backstop, the effective per-call cap is no
    longer than that backstop, and the run records that the declared cap exceeds
    the backstop — in the trigger's resolved-configuration record (the
    workflow-log surface from step 3, which the trigger can compute: declared
    value against the backstop) and in the job log of a stage that actually
    clamps. A declared cap at or under the backstop is honoured unchanged.
  - *Test (extend):* the step 2 env-sandbox test gains the clamp case — a
    `CW_PI_TIMEOUT` longer than the backstop yields a pi call capped at the
    backstop — and the step 3 resolved-config test gains the exceedance line
    (the record names the declared value, the backstop, and that the declared
    cap is not honoured). Docstring cites
    `requirements/configuration.feature::A declared cap longer than the job's
    timeout backstop is not honoured`. Where the step touches the runtime tree,
    the same-commit `make embed` rule of step 2 applies.
  - *arc42 context:* consistent with chapter 5's bounded-loop machinery ("every
    stage's pi call carries its own time cap" — a call cut off at the cap is
    retried inside the loop, a slow model is not a broken environment): the cap
    stays a per-call property; the backstop merely bounds how long a target may
    ask a single call to run. No contradiction.

  - *Goal (AC6, adjusted existing requirement — its stated counts change from
