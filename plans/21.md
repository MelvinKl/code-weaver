# Issue #21 — Automatic release on main; single increasing version numbers

**Summary**

Two coupled changes to the code-weaver repo's release machinery (the delta's
own header: "the release trigger and the tag scheme change together"): a
change that lands on the `main` branch **automatically publishes the next
version** as a GitHub release, and that next version is **the next single
increasing number** — the old `vX.Y.Z` semver tags are gone from the release
flow — so a target never waits on a manual tag to pick up a factory change.
The change is confined to this repo's release machinery (`.github/workflows/release.yml`)
plus the documentation surfaces that describe it (chapters 8/11, README). The
factory's consumption surface is deliberately untouched: the target's
consumer workflow still invokes the factory as a reusable workflow at a
version tag (owner `MelvinKl`), keeps the `labeled`-only trigger, and an
upgrade remains a one-line ref bump — the standing `reuse-by-ref` /
`labeled-only-trigger` / `trigger` scenarios are unaffected, and this repo's
own consumer workflow keeps its older-scheme `@v0.1.3` pin, which the changed
scenario's own And line ("workflows pinned to an older ref keep working")
requires to stay valid.

**Description**

The changed requirements are this run's stage-4 extraction output (commit
"stage 4 requirements-extraction: generated (iteration 0)"): a **new file**
`requirements/auto-release-on-main.feature` (3 scenarios, all tagged
`@issue-21 @auto-release`), and a two-line edit inside
`requirements/reuse-by-ref.feature` — one scenario altered: "Every published
version is a stable ref" (When: "a maintainer tags a new release" → "a new
release is published"; Then: "the tag follows vX.Y.Z semver" → "its tag is a
single increasing version number"; the And line "workflows pinned to an older
ref keep working" is unchanged). The oracle on this branch is 15 files, 138
scenarios; the README and arc42 still state the pre-delta count (14 files,
130 scenarios — stale since the #43 topic placement) and Task 3 refreshes it.

The baseline the change replaces: `release.yml` fires on
`push: tags: ["v*.*.*"]` — a maintainer's manual semver tag — and publishes
a GitHub release from that tag (release notes diffing the changed factory
paths and telling consumers to bump their ref). The README documents exactly
that mechanism twice ("**Every published version is a stable ref**: tag
`vX.Y.Z` → GitHub release; targets pinned to an older ref keep working" in
"Upgrading is a ref bump"; "release.yml — tag vX.Y.Z → GitHub release (the
ref targets pin)" in the layout), as do arc42 chapter 8 ("`release.yml` turns
a `vX.Y.Z` tag into a GitHub release; tags are immutable, so targets pinned
to an older ref keep working, and bumping the ref is the only change a target
ever makes") and the glossary ("Reuse by ref … every published `vX.Y.Z` tag
is a stable ref"). The repo's published tags are older-scheme ones (the
consumer workflow's pin `@v0.1.3` is one of them).

Classification of the delta scenarios against the standing oracle:

| Delta scenario | Class | Standing counterpart |
|---|---|---|
| A change on main automatically releases a new version | **new** | — (no standing scenario covers the release workflow's trigger or any auto-publication) |
| The automatic release takes the next increasing number | **new** | — (no standing scenario pins any version-numbering scheme) |
| The release flow no longer carries the semver scheme | **new** | — (the standing `reuse-by-ref` scenarios pin the consumer's `uses:` ref form and owner, not the release workflow's trigger/tag configuration) |
| Every published version is a stable ref (`reuse-by-ref.feature`) | **adjusted** | the same scenario in its pre-change form (maintainer tags a new release → the tag follows `vX.Y.Z` semver); the change alters its When and Then, its And line (older refs keep working) is unchanged |

**The live documentation contradiction (called out and justified).**
Chapter 8, the glossary's "Reuse by ref" entry, and the two README sentences
above state the old mechanism (maintainer's manual `vX.Y.Z` tag → release) —
after this change they would describe a mechanism that no longer exists. The
delta supersedes them: the requirements files are the source of truth the
implementation must fulfil, and the review stage judges the scenarios of the
feature files this run changed against the result. This is resolved by the
implementation (Task 3 rewrites the mechanism statements), not routed to the
owner: the change touches this repo's release machinery only — a component
no factory stage depends on — so no stage contract is perturbed. The generic
statements that survive unchanged: "every published tag stays a stable ref"
(chapters 1 and 2) and the stability half of chapter 8 ("tags are immutable,
so targets pinned to an older ref keep working") remain true under the new
scheme, since both tag series (the older `vX.Y.Z` tags and the new
single-number tags) stay immutable, pinnable refs.

**Acceptance Criteria** (each mapped to the Gherkin scenario it fulfils):

- **AC-1** — a change merged into the code-weaver repo's `main` branch makes
  the release workflow create and publish a new version **without any
  maintainer action**, as a GitHub release that a target can pin like any
  published version.
  *(Scenario "A change on main automatically releases a new version" in
  `auto-release-on-main.feature` — **new**)*
- **AC-2** — where the repo's highest published version is N, the automatic
  release it triggers is tagged with the number after N; the version numbers
  of published releases never repeat and never decrease.
  *(Scenario "The automatic release takes the next increasing number" —
  **new**)*
- **AC-3** — read for what it is, the release workflow's trigger and tag
  configuration fires on the main branch's advance rather than on a
  maintainer's manual tag, and it creates no semver `vX.Y.Z` tags.
  *(Scenario "The release flow no longer carries the semver scheme" —
  **new**)*
- **AC-4** — every published version is a stable ref: the tag of a newly
  published release is a single increasing version number, and workflows
  pinned to an older ref (including the pre-change `vX.Y.Z` tags) keep
  working.
  *(Scenario "Every published version is a stable ref" in
  `reuse-by-ref.feature` — **adjusted**: its When changed from "a maintainer
  tags a new release" to "a new release is published", its Then from "the tag
  follows vX.Y.Z semver" to "its tag is a single increasing version number",
  its And line unchanged)*
- **AC-5** — the factory's consumption surface is undisturbed: a target's
  workflow still invokes the factory as a reusable workflow at a version tag
  (owner `MelvinKl`), the consumer's declared trigger stays `labeled`-only,
  and an upgrade is still a one-line ref bump.
  *(Scenarios "The factory is invoked as a reusable workflow" and "An upgrade
  is a ref bump" in `reuse-by-ref.feature`, and the `labeled-only-trigger`
  scenarios — **unchanged**; the change must leave them satisfied)*
