# Issue #20 — Labeled-only factory trigger

**Summary**

Restrict the code-weaver trigger (`on.issues.types`) to `labeled` only — in both the
README's "Consume it (by ref)" example and the consumer workflow this repo deploys on
itself (`.github/workflows/code-weaver.yml`) — so that opening or editing issues no
longer schedules factory runs; only a label addition (and the unchanged manual
dispatch) does. The reusable factory (`factory.yml`) is deliberately untouched — its
stage-1 label gate is event-agnostic — so the change lives entirely in the consumer
layer plus the documentation and tests that pin it.

**Description**

The changed requirement is this issue's stage-4 extraction output,
`requirements/issue-20-labeled-only-trigger.feature` — a new file with 7 scenarios
(all tagged `@issue-20 @trigger`), whose header states the consequence: "opening or
editing issues no longer fires the workflow — only a label addition (and manual
dispatch) does". Against the baseline, both declared triggers were
`types: [opened, edited, labeled]` (the consumer workflow and the README example);
both are now `types: [labeled]`.

Classification of the 7 delta scenarios against the standing oracle:

| Delta scenario | Class | Standing counterpart |
|---|---|---|
| The README example shows a labeled-only trigger | **new** | — (no standing scenario pins the documented example's trigger shape) |
| The repo's own deployed workflow uses a labeled-only trigger | **new** | — (the reuse-by-ref scenarios pin the factory `uses:` ref and owner, not the consumer's event types) |
| The documented example and the deployed workflow agree on the trigger | **new** | — |
| Adding the trigger label still starts the factory and records the issue | **adjusted** | `trigger.feature` "Editing an issue to add the label starts the factory" — the change re-declares the trigger surface that scenario presupposes (`[opened, edited, labeled]` → `[labeled]`); its When step and expected outcome are unchanged |
| Adding a label that is not the trigger label leaves the factory idle | **adjusted** | `trigger.feature` "An issue without the label does not start the factory" — the delta refines it to the explicit form (the workflow fires for the `labeled` event; the trigger stage finds no trigger label and stays idle) |
| Opening an issue does not start a factory run | **new** | — (under the baseline declaration, opening *did* schedule a run; no standing scenario constrained the consumer's event types) |
| Editing an issue without a label change does not start a factory run | **new** | — (same as above) |

**The one live contradiction on this branch.** `requirements/trigger.feature` is
byte-identical to `origin/main` and still carries the standing scenario "Issue
opened with the label starts the factory" (When: "the issue *carries* the label
`ai-requirements`" — i.e. labelled at creation; Then: "the factory workflow runs").
Under the labelled-only trigger that outcome no longer holds — an issue opened with
the label attached schedules no run at all — so the unchanged older file contradicts
the newly changed file (and `PLAN.md` §7 already cites the post-change form of that
scenario). The change therefore **alters** that standing scenario: its When step
must become "the label `ai-requirements` is *added* to the issue" and its name
"An opened issue starts the factory once the label is added" (the Then steps — the
factory runs and records the issue number and body — are unchanged, and are fulfilled
by the `labeled` event, i.e. delta scenario 4). No other standing scenario is
affected: "Editing an issue to add the label…", "An issue without the label…", the
configurable-label, manual-dispatch, broken-runner, idempotency and resume scenarios
all hold unchanged under a labelled-only trigger (the stage-1 gate is event-agnostic).

Per the factory's design `requirements/` is **read-only to every stage**: the
extract guard pins "exactly one new file named after the issue — a changed existing
file is a guard violation, reverted and re-run"; the implement guard reverts
requirement edits and loops back to planning; and `docs/10` ("Extraction delta
shape") states the rule for exactly this case: "A delta that genuinely contradicts
an existing scenario is reported in the model's reply and resolved by the review
stage — the oracle stays the single source of truth." This plan therefore does not
direct the implement stage to reword the standing scenario (that edit would be
reverted, the plan regenerated against the unchanged requirement, and the loop cap
burned). It **specifies** the consistent rewording and **routes** the supersession
through the designed report path — the open item in `docs/10`, the plan (which
feeds the pi-generated PR body), and the final status report — leaving the oracle
edit itself to the owner as a follow-up.
