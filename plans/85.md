# Issue #85 — Brownfield targets: extract the full requirements from a project without a requirements dir, and scope the plan and the implementation to the test references

**Summary**

Teach the factory to work a **brownfield** target — a project that already
has code, documentation and tests but no `requirements/` directory (a first
factory run on that project): the requirement-extraction stage derives the
**full** requirement set from the project's current code, documentation and
tests (a source the project lacks is skipped, never fatal) and writes it as
`.feature` files that create the requirements directory; the planning stage
names the extracted scenarios and scopes every plan task to adjusting the
tests to reference them — no plan task implements code; and the
implementation stage changes **no source code** on such a run — the changed
files are the tests (adjusted to cite the scenarios they implement) and the
issue's plan file. The existing "empty issue body writes nothing" stop is
conditioned on the target *having* a requirements directory, and the
README/arc42 surfaces state the new behaviour and the oracle counts as they
move with the grown tree (16 files, 172 → 175 scenarios).

**Description**

The delta touches three requirement files — one **adjusted** scenario and
three **new** `@brownfield` scenarios, all in existing topic files (no new
feature file, so the tree grows to **16 files, 175 scenarios**):

- `requirements/requirement-extraction.feature` — the standing scenario
  "An empty issue body does not produce invented requirements" gains the
  Given **"the target project has a requirements directory"** (the stop is
  now conditioned on it), and the new scenario **"A first-time run without
  a requirements dir extracts the full requirements"**: a target without a
  requirements directory is a first factory run on that project, and the
  extraction derives the full requirement set from the project's current
  code, documentation and tests — a source the project does not have is
  skipped rather than failing — written as `.feature` files that create the
  requirements directory.
- `requirements/plan.feature` — the new scenario **"A brown field plan
  scopes its tasks to the test references"**: on a run whose requirements
  were extracted from the project's existing code, the plan names the
  extracted scenarios it must cover, its tasks are scoped to adjusting the
  tests to reference those scenarios, and no plan task implements code.
- `requirements/implement.feature` — the new scenario **"A brown field run
  adjusts the tests without implementing code"**: on such a run the
  implementation changes no source code — the changed files are the tests
  and the issue's plan file; the existing tests are adjusted to reference
  the requirements they describe; each adjusted test that implements a
  scenario cites it in its docstring as `<feature file>::<scenario name>`.

Shape of the implementation: the stage machinery already carries every
mechanism the brownfield path reuses, so the work is (a) a new branch in the
extract stage's entry logic plus a first-run clause in the requirements
prompt, (b) a brownfield scope clause in the plan prompt attached by the
plan stage when the delta it carries is the all-new-files shape, and
(c) a brownfield clause in the implement prompt. The recognising rule the
plan and implement stages share: the run's delta is the brownfield shape
when **every** requirement file that changed against the baseline is *new*
(the extraction created the requirements directory, so the baseline knows
none of them). No guard changes: the extract guard's allow set (the
requirements dir) already admits the files that create it, and the
implement guard's inverted-allow shape (deny = requirements + plans; the
current issue's plan file re-allowed; everything else admitted) already
admits the brownfield change set — the guard protects the protected set, it
does not dictate where work belongs. The review stage changes nothing: its
delta-scoped verdict (the scenarios of the feature files this run changed,
plus the scenarios the run's changed tests reference) already covers the new
scenarios on this run and, on a real brownfield target, judges the adjusted
tests by the requirements they reference. This run is the dogfood on the
factory's own repo (which has a requirements dir), so the brownfield
scenarios are pinned here by sandboxed stage-contract tests; an actual
brownfield target exercises them end-to-end through the unchanged
guard/review machinery.

**Acceptance criteria**

- **AC1** — Where the target project has **no** requirements directory (a
  first factory run on that project), the extraction stage runs pi to derive
  the **full** requirement set from the project's current code,
  documentation and tests; a source the project does not have is skipped
  rather than failing the extraction; the requirements are written as
  `.feature` files that create the requirements directory.
  *(Fulfilled by Task 1; scenario: "A first-time run without a requirements
  dir extracts the full requirements" — new.)*
- **AC2** — Where the issue body is empty or describes no change **and the
  target project has a requirements directory**, no requirement file is
  written and the factory reports "no delta requirements" and stops cleanly.
  *(Fulfilled by Task 1; scenario: "An empty issue body does not produce
  invented requirements" — adjusted: the new Given step "the target project
  has a requirements directory" narrows the stop's precondition; the Then
  outcomes are unchanged.)*
- **AC3** — On a run whose requirements were extracted from the project's
  existing code, the plan stage runs pi with a prompt that makes the plan
  name the extracted scenarios it must cover, scope the plan's tasks to
  adjusting the tests to reference those scenarios, and carry no task that
  implements code.
  *(Fulfilled by Task 2; scenario: "A brown field plan scopes its tasks to
  the test references" — new.)*
- **AC4** — On such a run the implementation works the plan so that no
  source code changes — the changed files are the tests and the issue's plan
  file; the existing tests are adjusted to reference the requirements they
  describe; each adjusted test that implements a scenario cites it in its
  docstring as `<feature file>::<scenario name>`.
  *(Fulfilled by Task 3; scenario: "A brown field run adjusts the tests
  without implementing code" — new.)*
- **AC5** — The documented surfaces state the brownfield behaviour and the
  oracle counts as the tree now holds them: every surface that states the
  oracle counts states 16 files / 175 scenarios, and the README and arc42
  stage descriptions carry the conditioned empty-body stop, the first-run
  full derivation, and the brownfield plan/implementation scope.
  *(Fulfilled by Task 4; scenarios: "The documented oracle counts match the
  requirements tree" (requirement-extraction — existing, unchanged; the
  stated counts simply move with the grown tree), "The README is kept
  current" and "The arc42 documentation is updated and complete"
  (implement — existing, unchanged; the changed behaviour is what they now
  require reflected).)*
