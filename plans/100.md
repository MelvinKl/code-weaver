# Issue #100 — The single-pin rewrite stored the runtime tree in the workflow file as a base64 tarball: the published file is binary and past its max allowed size (500kb); retire the embed, and let the first job fetch the called version's tree at the called ref

## Summary

The single-pin rewrite made the reusable workflow self-carrying by storing
the runtime tree (the `.github/scripts` plumbing, the `.github/actions`
stage scripts, the `pi-prompts` templates) **inside** `.github/workflows/factory.yml`
as a base64 tarball behind the heredoc in stage 1's first step. That is a
binary payload in a file that must be plain text, and its bloat took the
published file past its max allowed size — **500kb** (528kb when the issue
was filed; 543,581 bytes in the current tree). This change retires the
embed:

1. the file **keeps its inlined stage steps**, stores **no binary content**,
   and is **at most 500kb**;
2. the runtime tree reaches the stage jobs the way the one-ref architecture
   already implies: the called ref selects a published **version** — the tag
   points at a commit of the factory repo whose tree carries **both** the
   workflow file and the runtime tree — and the **first job of the run
   fetches the called version's runtime tree into the runner's temp dir
   before the first checkout replaces the workspace**, resolving the called
   ref from the consumer workflow itself, so the consumer's `uses:` line
   stays the only pin the run makes (the consumer relays nothing; the
   `(legacy) factory-ref` input stays declared and is read by no stage);
3. the **release flow's publication gate** generalises from "the file's
   embedded payload is fresh" to "the published version is consistent" —
   plain-text file, file within the max allowed size, and the tagged
   commit's tree carrying the runtime tree the file's stage steps execute —
   so an inconsistent version (and a file past 500kb) is never published.

The one-ref version architecture is unchanged: the ref still selects the
published version — the file and the tree of that ref's commit — and a
target's ref bump still upgrades the factory atomically, with no separate
ref to keep in step.

## Description

The delta is a **standing in-place change** to the existing
`requirements/reuse-by-ref.feature` (the file predates the run's baseline;
the brownfield clause does not apply). It **adjusts seven scenarios in
place** — the embed clauses of each are reworded — and **adds two**:

- **Adjusted:** `The factory is invoked as a reusable workflow` ("one pin:
  **the ref selects the published version**, so no relayed ref accompanies
  it") · `The factory workflow is self-contained` ("the file stores **no
  binary content** — the runtime tree its steps execute is not embedded in
  it") · `The stage jobs materialise the runtime tree before their first
  checkout` (the first job "**materialises the runtime tree** into the
  runner's temp dir before the first checkout replaces the workspace") ·
  `The whole version is one ref` ("**the ref's published version carries the
  file and the tree together, and the file stores no binary payload**" /
  "the tree the run executes is **the one the ref's version carries**") ·
  `A run triggered in the factory's own repo works on that repo's code`
  ("the tagged version's tree, **kept consistent with the file by the
  release flow's publication gate**" / "the file and its runtime tree as one
  published version") · `The README's consumption pattern works on a target
  repo` ("the tree of the called version (the consumer relays nothing)") ·
  `A published version is self-contained` ("stage steps inlined in the
  file, **which stores no binary payload**" / "the whole version — the
  workflow's stage steps and its runtime tree, the trigger's artifact
  carrying the tree across jobs — is selected by that one ref, **the file
  storing no binary payload**").
- **Added (new):** `The factory workflow file stays within the max allowed
  size` (measured **at most 500kb**) · `The factory workflow file stores no
  binary content` (**plain text** — no base64 tarball embedding the runtime
  tree).

Net, the oracle's tree grows from **196 to 198 scenarios** (16 files
unchanged; the two additions sit in `reuse-by-ref.feature`, the in-place
adjustments change no count), while every documented surface still states
196 — the adjacent existing scenario
`requirement-extraction.feature::The documented oracle counts match the
requirements tree` is red until step 5 reconciles the stated counts.

The delta's header comment names the open question this plan answers:
*how the runtime tree reaches the stage jobs* — the oracle no longer pins
the tree to the file. The design this plan scopes:

- **The called ref is recoverable, so it needs no relay.** The runner
  fetched the factory's workflow file *from the factory repo at the ref the
  consumer's `uses:` line declared*. Reading the consumer workflow as
  committed at the run's base ref (fetched over the API — no checkout has
  happened yet, so nothing has replaced the workspace) recovers exactly the
  ref that selected the file. The first job fetches the factory repo **at
  that same ref** — one ref, one version: the file that runs and the tree
  its steps execute are the two halves of the tag's commit. No second ref
  enters the run, and the consumer's workflow gains no line: the `uses:`
  line is the only pin, and the `(legacy) factory-ref` input stays declared
  (an older consumer's `with:` block stays schema-valid) while no stage
  reads it.
- **The fetch must work on every target under the documented token
  contract.** The chapter-3 constraint and the README pin `GH_TOKEN` as
  "a token that **can read the target repo**" (repo-scoped; a fine-grained
  PAT scoped to the target repo). Such a token cannot read a different
  repo — even a public one — so the factory fetch **must not ride that
  token**: the factory repo is public (the oracle pins consumption of the
  public `MelvinKl` release line), and the fetch is a public-repo fetch
  (the target-scoped token is used only to read the consumer file in the
  target repo, which that contract already requires). The delta rewords no
  token constraint, so the plan keeps it untouched.
- **The 500kb max allowed size is undocumented in the arc42 set.** No
  chapter names a size limit for the workflow file — the two new scenarios
  are the sole source for it. The plan says so and plans around it: the
  cap becomes an enforced property of the published file (the publication
  gate fails a publish whose file exceeds it, and the new suite test pins
  the current file against it), and the naming is planted where the
  version's shape is documented (chapter 8's release-flow paragraph and the
  README's layout line) rather than assumed from an absent chapter.
- **Already-published versions are immutable and keep their own mechanism.**
  Tags cut before this change carry the embedded form (the file decodes its
  own payload; those files were published under the old gate). The standing
  scenario "workflows pinned to an older ref keep working" must stay true —
  it does: each published version is self-sufficient under its own
  mechanism (old tags decode; tags cut from this change on fetch the called
  version's tree), so no cross-version coupling is introduced. The
  publication-gate generalisation governs the versions published from this
  change on.
- **What stays unchanged:** the file's inlined stage steps (self-contained —
  no composite actions, no own-action refs, every stage step declares its
  shell); the per-job stash layout (`$RUNNER_TEMP/cw/stash`, repo-relative,
  the stage scripts' `__file__`-relative resolution and the report stage's
  dual-path plumbing ride it); the trigger's artifact carrying the tree to
  every later stage job (hidden-file opt-in included); the later jobs'
  download-and-restore before their first checkout; the consumer workflow's
  shape (owner, repo, path, version tag, `with:`/`secrets:` blocks,
  `labeled`-only trigger); the release flow's shape (fires on the main
  branch's advance; never pushes a commit that updates a workflow file — the
  publishing principal is refused the `workflows` scope; the tag is the
  only ref it publishes; one tag per commit; a push confined to the
  consumer workflow spends no release number; the default token publishes).
