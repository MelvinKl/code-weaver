# Issue #58 — PR description parity: same usage numbers as the issue
comment, the body describes the implemented issue, and the issue closes
after a successful run

**Summary**

Three fixes to how the factory's pull request and source issue read after a
run (observed on PR #57 / issue #21: the issue comment posted the run's
token usage and cost while the PR description — a generic
"Resolved configuration" dump that even rendered the issue as `# —` —
carried neither, and the issue stayed open after a green run):

1. **The PR description and the issue comment carry the same usage
   numbers.** The report stage (15) re-reads the PR after editing its body
   and only then keeps the pointer comment ("final status is in the PR
   body"); where the completion could not be applied — the PR was already
   merged, or the edit was refused on both write paths (the `gh pr edit`
   GraphQL mutation and the REST `PATCH /pulls/{n}` fallback) — the issue
   comment carries the full final status itself (usage lines + stage
   outcomes) instead of claiming the PR body carries it. Both surfaces are
   assembled from the same usage ledger, so the numbers are identical by
   construction.

2. **The PR description describes the issue the run implements, not the
   configuration the run used.** The pi prompt (`pi-prompts/pr-body.md`)
   now states that explicitly and bans the resolved-configuration dump and
   any self-written `## Final status` section (stage 15 owns it). The
   template fallback (used when the pi call produced no body) is rewritten
   to the same shape: the issue's number and title read from the trigger's
   state files — the authoritative channel, since this runner build's
   job-env relay has been observed dropping those values (the body that
   once opened for `issue: # —`) — the issue's plan embedded, and the
   requirement scenarios the run changed (the added scenario title lines
   of the diff against the trigger's baseline sha).
   The resolved configuration stays where it belongs: the workflow log.

3. **A successful run closes the source issue.** The report stage closes
   the issue (`state=closed`, `state_reason=completed`) after posting the
   success comment; the close is best-effort (a refusal is warned, not
   fatal) and a failed run leaves the issue open for a re-trigger. Merging
   the PR remains a human decision.

**Description**

The changed requirements are deltas in two standing topic files:
`requirements/reporting.feature` gains three scenarios — "The PR
description carries the same usage numbers as the issue comment", "A
successful run closes the source issue", "A failed run leaves the source
issue open" — and `requirements/pr-and-gates.feature` adjusts "A pull
request is opened against the target branch" (the PR body also describes
the issue the run implements) and gains "The PR body describes the issue
it implements". The standing reporting scenarios "The final status report
is the PR", "The source issue is commented with the outcome" and "A
failed run is reported too" stay satisfied: the comment is still posted,
the failure report is unchanged in content, and the PR is still the report
where it can be completed.

**Acceptance Criteria** (each mapped to the Gherkin scenario it fulfils):

- **AC-1** — the report stage verifies the PR-body completion actually
  landed (re-reading the PR after the edit, with a REST-edit fallback
  before giving up) before the comment claims "final status is in the PR
  body"; where the completion could not be applied, the comment carries
  the full final status itself — same usage lines, same stage outcomes —
  and makes no claim about the PR body.
  *(Scenario "The PR description carries the same usage numbers as the
  issue comment" — **new**; both surfaces are built from the same `usage_lines`
  assembled from the run's usage ledger, so the totals and the cost are
  identical on the PR description and the issue comment)*
- **AC-2** — a run that reached the report stage with result `success` has
  its source issue closed with the `completed` state reason, and the issue
  comment states the run result and the issue's closed state; the factory
  still does not merge the PR.
  *(Scenario "A successful run closes the source issue" — **new*;
  adjusts the standing "The source issue is commented with the outcome",
  whose comment is unchanged in content and gains the close outcome)*
- **AC-3** — a run that reached the report stage with result `failure`
  leaves its source issue open for a re-trigger; only the failure summary
  is commented on it.
  *(Scenario "A failed run leaves the source issue open" — **new*;
  consistent with the standing "A failed run is reported too")*
- **AC-4** — the PR body (pi-generated or template fallback) states the
  source issue's number and title, summarises what the issue asked for
  from the plan and the requirement delta, lists the requirement
  scenarios the run changed (the delta's added scenario lines), and
  carries no resolved-configuration dump;
  where the job-env relay dropped the trigger's values, the body still
  names the issue (read from the trigger's state files).
  *(Scenario "The PR body describes the issue it implements" — **new*;
  extends the standing "A pull request is opened against the target
  branch" and "The PR body links back to the work", both unchanged in
  their pinned content)*
