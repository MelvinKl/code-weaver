# Issue #18 — Release changelog becomes a per-commit table; the pipeline gains a dependency-upgrade stage (default on, configurable off)

**Summary:** The delta touches three requirement files and has two mechanisms.
(1) `auto-release-on-main.feature` — the release notes' changed-since content
changes form: it becomes a **table with one row per commit** in the branch
since the release's range base, each row carrying the commit's title, its
author, its hash and its datetime. The two standing issue-79 notes
scenarios are updated in place to the table form; their range-base rules
(predecessor release as base, first commit only without one, never empty)
stay, and one new scenario pins the table itself.
(2) The project-dependencies topic **gains a second mechanism** beside the
existing dependency-install step: the factory's pipeline runs a
**dependency-upgrade** that upgrades the target project's dependencies to
newer versions — **default on, configurable off** through the consumer
workflow (a new setting on the documented configuration surface,
`configuration.feature`), running **before the implementation stage**,
**without breaking the project's current functionality** (its test suite
still passes against the upgraded dependencies), and **described in the
README and the arc42 documentation** (the file's new `@docs` scenario).

**Scope note.** The delta is the **standing in-place shape**, not the
brownfield one: every changed file exists in the baseline, the change is
in-place scenario adjustments (two in `auto-release-on-main.feature`) plus
new scenarios inside the three existing topic files — five scenarios in all,
**no new feature file** (the tree stays at 16 files and grows 180 → 185
scenarios). The requirements files are already in the tree and are the
protected set — this plan implements the code, tests and documentation that
fulfil the delta; it edits no requirement file.

## Acceptance Criteria

- For a release that has a predecessor release, the notes' changed-since
  reference is the predecessor release and not the first commit, and the
  notes' changelog is a table with one row per commit in the branch since
  the predecessor release.
  → `requirements/auto-release-on-main.feature::The release notes name the changes since the previous release`
  (**adjusted** — the delta rewords the scenario's second Then line from the
  file-list form to the table form; its range-base rule is unchanged)
- For a release published for a push that changed at least one file, the
  notes' changelog table is not empty; the table carries one row per commit
  in the branch since the release's range base; where the release has no
  predecessor its range base is the first commit and its table is still not
  empty.
  → `requirements/auto-release-on-main.feature::The release notes are never empty for a release that publishes changes`
  (**adjusted** — same in-place rewording to the table form; the
  never-empty and range-base-dichotomy properties stay)
- For a release published whose branch carries commits since the previous
  release, the changelog is a table; the table has a row for every commit in
  the branch since the previous release; each row carries the commit's
  title, the commit's author, the commit's hash and the commit's datetime.
  → `requirements/auto-release-on-main.feature::The release changelog is a table of the commits since the last release`
  (**new** — no existing scenario covers the changelog's table form)
- The dependency-upgrade setting is configurable: its default is on; a
  target turns it off via its workflow inputs; the run's pipeline runs
  without the dependency-upgrade stage; and the run's stages, pull request
  and final status report are unchanged by the upgrade's absence.
  → `requirements/configuration.feature::The dependency-upgrade setting is configurable`
  (**new**)
- For a target project with pinned project dependencies and the
  dependency-upgrade setting at its default, the run's pipeline upgrades the
  project's dependencies to newer versions, and the dependency-upgrade stage
  runs before the implementation stage.
  → `requirements/project-dependencies.feature::The factory's run upgrades the target project's dependencies`
  (**new**)
- For a target project whose test suite passes on the run's baseline, the
  dependency upgrade keeps it passing against the upgraded dependencies, and
  the run's stages that consume the dependencies work against a project whose
  functionality is intact.
  → `requirements/project-dependencies.feature::The dependency upgrade does not break the project's current functionality`
  (**new**)
- A target maintainer reading the README for how to run the factory finds that
  it describes the dependency-upgrade stage and how a target turns it off,
  and the arc42 documentation covering the same mechanism states the same.
  → `requirements/project-dependencies.feature::The README and the arc42 documentation describe the dependency-upgrade stage`
  (**new**, `@docs`)
- The documented oracle counts match the requirements tree: this delta grows
  the tree from 180 to 185 scenarios (16 files, none new), so the counts the
  README and arc42 surfaces state must move with it.
  → `requirements/requirement-extraction.feature::The documented oracle counts match the requirements tree`
  (**standing** — neither new nor adjusted in this delta; the tree growth is
  what makes the stated 180 stale, so the plan keeps it green)

## Steps

The implementation stage works this list top to bottom, flipping each box
when done. Step 1 is independent. Steps 2 → 3 are ordered (the stage gates on
the setting). Steps 4 and 5 are the documentation work, edited in that order.

- [x] **1. The release notes' changed-since content is rendered as a table
      with one row per commit**

  1. *Goal and its requirements.* Fulfil the **new** requirement "The
     release changelog is a table of the commits since the last release" and
     the two **adjusted** standing requirements "The release notes name the
     changes since the previous release" and "The release notes are never
     empty for a release that publishes changes" (AC 1–3). In
     `.github/workflows/release.yml`'s Publish step: the notes' changed-since
     content — currently the file list `CHANGES=$(git diff --stat "$RANGEFROM"
     HEAD | tail -n +2)` — is rendered as a markdown **table with one row per
     commit** in the branch since the range base, each row carrying the
     commit's title, its author, its hash and its datetime (the range is
     enumerated over the range base the workflow already computes; the exact
     `git log` pretty-format and the table's header line are
     implementation details — the table shape is what the oracle pins).
     Rendered **inline in the workflow step** — no `.github/scripts` change,
     so the embedded runtime tree and its `make embed` freshness gate are
     untouched (unlike issue 79's helper change, `release.yml` is not part of
     the embedded tree). Kept unchanged, per the delta's own header note
     ("their range-base rules … stay"): the predecessor release's tag as
     range base, restricted to the numbered series (`git describe
     --match '[0-9]*'`); the first commit only where no predecessor exists
     (`RANGEFROM=${PREV:-$(git rev-list --max-parents=0 HEAD)}`); the notes'
     range-base reference line (`${PREV:-the first commit}`); the full-history
     checkout (`fetch-depth: 0`); and the flow's remaining behaviour — the
     number computation, the one-tag-per-commit guard, the
     consumer-workflow-only push skip, the tag-only push, the tokenless
     `gh release create`.
  2. *The test that proves it.* In `tests/test_release_contract.py`,
     **edit** the two tests the delta's in-place scenario updates make
     stale — `test_release_notes_name_the_changes_since_the_previous_release`
     and `test_release_notes_are_never_empty_for_a_release_that_publishes_changes`
     both currently pin the file-list form (`git diff --stat "$RANGEFROM"
     HEAD`; the "no pathspec subset" check): re-pin them to the table form —
     the notes enumerate one row per commit over the range base → HEAD range
     (in the second test, over the whole range, not a subset of it) — while
     keeping every assertion the scenario keeps: the predecessor tag derived
     via `git describe --match '[0-9]*'`, the `RANGEFROM=${PREV:-…}`
     dichotomy, the notes' range-base reference, and the full-history
     checkout. An unchanged older test next to the newly reworded scenario is
     a contradiction the review stage flags. **Add** to the same module the
     test for the new scenario (docstring citing `requirements/
     auto-release-on-main.feature::The release changelog is a table of the
     commits since the last release`): the notes' changelog is a table, the
     table has a row for every commit in the branch since the previous
     release, and each row carries the commit's title, the commit's author,
     the commit's hash and the commit's datetime. The helper's existing
     pure-function tests (number series, one-tag-per-commit guard, the
     changed-files skip) stay green unedited — step 1 changes no script.
  3. *arc42 context.* Chapter 8 (deployment view) and the README's
     "Upgrading is a ref bump" paragraph describe the release notes as
     "name the changes since the predecessor release — the first commit only
     where there is no predecessor — and are never empty for a release that
     publishes changes." That wording pins exactly the range-base rule and
     the never-empty property the delta explicitly keeps, so it stays true of
     the table form: **no documentation edit is required by this step, and no
     documented surface is contradicted.** (Where the implementation stage
     chooses to reword those sentences, it keeps the stated rule identical.)

- [x] **3. The dependency-upgrade runs before the implementation stage, and
      skips when the setting is off**

  1. *Goal and its requirements.* Fulfil the two **new** requirements "The
     factory's run upgrades the target project's dependencies" and "The
     dependency upgrade does not break the project's current functionality"
     (`requirements/project-dependencies.feature`), and complete the
     **new** configuration requirement's pipeline half. The factory's
     pipeline gains the dependency-upgrade mechanism as an **inlined step in
     the existing `implement` job** — the job whose stage is the
     implementation stage (stage 8) — placed **after the job's checkout of
     the AI branch and before the stage's step, and before the job's
     stage-baseline recording**, so the step's footprint is never counted as
     the stage's work by the guard (the documented dependency-install
     placement idiom, chapter 7). The documented self-contained shape is
     preserved: inlined workflow text, **no new job** — the 15-stage/9-job
     pipeline count stays (chapters 4, 5 and 11 state it; see the
     contradiction note in 3). Where the setting is **on** (the default): the
     step upgrades the project's dependencies to newer versions and the
     upgrade's footprint is **committed to the AI branch** — dependency
     files sit inside the implementation's lane (the guard's inverted allow
     admits everything except the protected requirements/plans set, chapter
     6), so the commit rides the implementation's branch work and the guard
     never reverts it — which is what carries the upgraded project across job
     boundaries: each job's checkout replaces the workspace, and the branch
     is the only documented cross-job workspace channel (chapter 7). The
     consuming stages then work against an upgraded, intact project: the
     implementation stage in the same job, and the `review` job, whose
     documented checkout + dependency-install step materialises the upgraded
     environment for the `make test` suite run. The step's concrete upgrade
     command is a design decision inside the documented constraints — the
     factory is target-agnostic (chapter 4: "any GitHub repo"), and the
     documented channel by which a target names commands for its own project
     environment is the `dependency-install` input; a target that declares
     none has no upgrade to run and the step is a no-op, mirroring that
     input's documented no-op property. Where the setting is **off**: the
     step is a **no-op** — it guards on the value relayed through the
     documented step-env idiom (step 2's setting, relayed as
     `CW_DEPENDENCY_UPGRADE: ${{ inputs.dependency-upgrade }}`), logs the off
     case and exits without touching the workspace (the documented no-op
     idiom) — the pipeline runs without the stage: no other job gains a step,
     and the run's stages, pull request and final status report are unchanged
     by the upgrade's absence.
  2. *The test that proves it.* **Add** tests to
     `tests/test_dependency_install_contract.py` (the module that pins the
     `project-dependencies.feature` topic — the new scenarios extend the same
     topic file, and each new test cites its scenario in its docstring per the
     test-reference convention the suite-level stage-contract test enforces):
     (a) a placement test citing "The factory's run upgrades the target
     project's dependencies" — the `implement` job carries the upgrade step,
     positioned after its AI-branch checkout and before its stage step, with
     the stage-baseline recording after the step and the setting relayed
     through the documented step-env idiom, the step executing where the
     setting is at its default (on) — plus the unchanged-run half, mirroring
     the module's existing `test_undeclared_target_runs_unchanged`
     job-sweep idiom: no other job carries the step, and where the setting is
     off the step's no-op path guards, logs and exits before touching the
     workspace (this pins the off path of "The dependency-upgrade setting is
     configurable"); and (b) a functionality-intact test citing "The
     dependency upgrade does not break the project's current functionality" —
     the upgrade's footprint reaches the consuming stages through the AI
     branch (the review job's checkout is the documented cross-job channel),
     and the review job's existing documented dependency-install step then
     installs the upgraded set for the suite run, so the suite (which
     executes every scenario) runs against a project whose functionality is
     intact.
  3. *arc42 context.* Touched and preserved: chapter 5 (the pipeline's
     stage/job table, and "the step is inlined workflow text, not a new
     component — no new job is added, the 15-stage / 9-job pipeline count
     stays, and the self-contained shape is preserved" — said of the
     dependency-install mechanism, and held for the upgrade step the same
     way); chapter 6 (the `implement` job's inlined steps and its
     inverted-allow guard — dependency files are inside the implementation's
     lane, so the upgrade's commit is admitted, never reverted); chapter 7
     (runtime view — the per-job checkout, the stage-baseline recording that

     the documented "Project dependency-install step" entry is the model for
