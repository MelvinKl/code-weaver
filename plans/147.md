# 147 — The run's pi harness is provided per run via GitHub secrets only: the repo's `.pi` directory is removed, a named repo file is no longer a provider of any harness element, the guard serves four checks, and the trigger scenario is reworded to the label-added form

**Summary.** Four requirement files changed against the run's baseline. `setup-pi.feature` adds three scenarios and rewords six: issue 147 removes the repo's `.pi` directory, so every harness element (the model configuration, the additional packages, the MCP configuration, the extension's environment variables) is set by the run's environment variables — the GitHub secret the consumer workflow's `secrets:` block carries — and a run whose environment provides no model configuration fails the setup stage clearly. `guard-rail.feature` rewords four scenarios: the shared guard now serves **four** checks (the update-check — added with the update stage in the prior run, the requirements directory as its lane — sits between the requirement-check and the plan-check), stated as "one script, four call sites". `safety.feature` drops the repo-file half of "The LLM backend needs no secret" (via a GitHub secret, not a pre-requisite of the runner environment). `trigger.feature` rewords "Issue opened with the label starts the factory" to "An opened issue starts the factory once the label is added" — the label-added (labeled-event) form, which the labeled-only consumer trigger already implements.

The delta is a standing in-place change of existing files (each diff rewords baseline content) — not the brownfield all-new-files shape — so the standing instructions govern: the steps below adjust the implementation where the changed behaviour requires machinery, and edit the tests that pin the changed surfaces so code, oracle and tests stay consistent. Oracle arithmetic: the baseline tree holds **179 scenarios in 17 files**; the delta adds exactly three scenarios (all in `setup-pi.feature`), the file count is unchanged, so the post-run tree holds **182 scenarios in 17 files** — every documented count the oracle-count test reads must move with it.

**Description.** The implementation surfaces the delta touches, per the arc42 and the README: the setup-pi stage script (`.github/actions/setup-pi/stage.py` — its `resolve_provider` pair "a non-empty GitHub secret wins over the named repo file"), the factory workflow (the `workflow_call` `secrets:` block and its comments, the `llm-model` input description, the trigger's resolved-config record, the setup-pi job's env comment, the report job's comment), the dogfood consumer workflow's secrets comment (`.github/workflows/code-weaver.yml`), the report stage script (its model-configuration provider — "the report job resolves the same provider", chapter 6), the README (stage-list item 2, the Consume-it example comment, the "LLM backend is provided" paragraph, the harness table, the oracle counts) and the arc42 chapters (03 constraints, 05 solution strategy's guard idiom, 06 building-block setup-pi/report/oracle lines, 08 deployment's "The harness providers" section, 10 risks, 11 glossary Guard and Oracle entries). The test surfaces are `tests/test_setup_pi_stage.py`, `tests/test_harness_provider_contract.py`, `tests/test_setup_pi_docs_contract.py`, `tests/test_stage_contract.py` (guard-repair references; report-cost provider assertions) and `tests/test_trigger_contract.py`. `tests/test_oracle_counts.py` is a checker, not an input: it compares the doc surfaces' stated counts to the tree, so the docs must state 182.

**Acceptance Criteria** (each mapped to the Gherkin scenario it fulfils; **N** = new scenario in this delta, **A** = adjusted existing scenario):

- *setup-pi.feature*
  1. (N) **The .pi directory is removed from the factory repo** — the code-weaver repo's committed tree contains no `.pi` directory, and no file of the run's pi harness (a models file, a settings file, an mcp file, an extension) is committed in the repo.
  2. (N) **The run's pi configuration is set by environment variables** — when the setup stage resolves the harness for the run, each element's provider is the run's environment variables (the GitHub secrets the consumer workflow's `secrets:` block carries), and a named repo file is no longer a provider of any harness element.
  3. (N, @safety) **A run whose environment provides no model configuration fails the setup stage clearly** — the stage fails with an explicit error that the run's pi configuration is incomplete, and no later stage runs.
  4. (A) **The LLM backend configuration is provided for the run, not a pre-requisite of the environment** — the Given now reads "provided by the run's environment variables (the GitHub secret the consumer workflow's secrets block carries)"; the remaining outcomes (the backend is the one in that configuration; written into the agent directory the invocation resolves; the runner's pre-existing user-level configuration is never used) are unchanged.
  5. (A) **A provided file without a backend is not a usable configuration** — the Given now names "the GitHub secret that provides it"; the outcomes (explicit "no backend in the provided configuration" failure; the runner's user-level configuration never used as the run's) are unchanged.
  6. (A) **The additional packages are provided by a GitHub secret** — renamed from "…by a GitHub secret or a repo file"; the provider is the run's environment variables, and an empty or absent settings provider leaves pi without additional packages (the repo-file clause of the old scenario is gone).
  7. (A) **The MCP configuration is optional** — the last outcome drops the `.pi/mcp.json` content pointer: where the MCP configuration is provided via a GitHub secret, the stage writes it into the pi agent directory for the run; an absent MCP provider means the run's pi runs without MCP servers.
  8. (A) **The additional environment variables are provided via a .env-style GitHub secret** — the Given drops the `.pi/extensions/pi-jev-config.ts` pointer; the materialisation and the state-file/relay outcomes are unchanged.
  9. (A) **The documentation lists the harness providers** — the README and the arc42 deployment chapter list the providers as the GitHub secrets for the model configuration, the additional packages, the MCP configuration and the extension's environment variables, all set by env vars; state that a named repo file is no longer a provider of any harness element; and keep stating that an empty or absent settings provider leaves pi without additional packages.
- *guard-rail.feature*
  10. (A) **A clean stage passes the guard** — a clean requirement-check reports OK and the pipeline proceeds **to the update stage and then to the plan stage**.
  11. (A) **A leaking stage is repaired by a pi call, not restarted** — a clean re-check lets the pipeline proceed to the update stage and then to the plan stage without re-running the extraction stage.
  12. (A) **The allowed file set is per-stage** — the per-check sets now include **the update-check allows only `requirements/`** beside the standing lanes (requirement-check: only `requirements/`; plan-check: only `plans/`; implement-check: everything except `requirements/` and the other issues' plans).
  13. (A) **All four checks share one implementation** — renamed from "All three checks…"; the checks are implemented as one shared guard (**one script, four call sites**), each collecting the files changed against its own baseline, comparing them against its per-stage allowed set, and repairing a violation with a pi call.
- *safety.feature*
  14. (A) **The LLM backend needs no secret** — no API key secret is required, and the backend configuration is provided for the run **via a GitHub secret** (the "or a repo file" half is dropped), not a pre-requisite of the runner environment.
- *trigger.feature*
  15. (A) **An opened issue starts the factory once the label is added** — reworded from "Issue opened with the label starts the factory": given an issue is opened in the target repo, when the label `ai-requirements` is **added** to the issue, the factory workflow runs and records the issue number and the issue body.
