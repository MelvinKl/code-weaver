# Issue #70 — A bug-labelled issue skips the requirements extraction and is planned from the issue itself

**Summary**

Seven new Gherkin scenarios across five of the sixteen oracle files thread one
behaviour through the pipeline: an issue that carries the trigger label **and
the (newly configurable) bug label** (default `"bug"`) skips the
requirement-extraction stage entirely — no pi call is made for it, no
requirement file is written, the requirement check passes with nothing
changed — and the run proceeds to a plan built from the issue itself (its
number, title and body) instead of from an extracted requirement delta; the
final status report lists the extraction stage as *skipped*, never as
"stage complete". An issue without the bug label extracts exactly as before,
a bug-labelled issue with an empty body stops cleanly with "no delta
requirements", and the bug label is a per-target setting riding the same
documented configuration channel as every other setting. This run's
extraction also grew the oracle from 201 to 208 scenarios, so the documented
oracle counts must be recounted to the tree.

How the feature threads the pipeline: the reusable workflow's configuration
surface gains the bug label as an optional setting (default `"bug"`, a target
declares another value; the resolved value rides the documented settings
channel — input → job-env relay → resolved-configuration record in the
workflow log, never committed). The trigger stage records whether the issue
carries that label as part of its run state, which travels to every later
stage job through the trigger's artifact. The extract stage's entry logic —
documented as branching on whether the target has a requirements directory —
gains the skip branch: a bug-labelled run makes no pi call, writes no
requirement file, passes its check with nothing changed, and proceeds to the
plan stage; a bug-labelled issue with an empty body instead stops cleanly
with "no delta requirements" and is not forwarded. The plan stage's prompt
assembly gains the empty-delta branch: the instructions name no requirement
file as changed and carry the issue itself as what the plan must cover. The
report stage renders a skipped extraction as "skipped", never "stage
complete".

**Fix iteration (this run's review finding) — the no-delta stop is a
run-level signal, not a stage-local one**

The run's review marked
`requirement-extraction.feature::A bug-labelled issue with an empty body
stops cleanly instead of being forwarded` UNFULFILLED: the extract
stage's no-delta stop was stage-local (a stage-summary line plus its
completion marker — no state signal for later stages), so the plan job —
gated only on the trigger's started flag — ran `run_plan_stage()`
unconditionally, and this run's new plan bug-branch turned the
empty-body bug run into a plan generated from the issue title alone
("the issue body is empty — plan from the number and title"): the run
*was* forwarded to the plan stage, contrary to the scenario. The fix
makes the no-delta stop a run-level signal the plan stage checks before
its pi call:

- the extract stage, where it takes the no-delta stop (the bug-skip
  empty-body edge, and the standing empty-body stop alike), records the
  `no-delta-stop` flag in the run's state dir beside the trigger's
  recorded state — it rides the cumulative artefact chain to every
  later stage job, and the per-job env relay (each Read trigger state
  step's key list gains it), like the other trigger-state keys; the skip
  branch (the bug-labelled run's way through) records no flag;
- the plan stage checks that flag before `build_target()` /
  `run_generation_stage()`: set, it stops cleanly without a pi call —
  no plan file, and no prompt assembly (the bug branch's empty-body form
  is never reached) — and records its own outcome line on the
  stage-summary channel, which the report renders as skipped, never as
  "stage complete";
- the standing non-bug empty-body stop keeps its extract-stage
  behaviour (no requirement file written; "no delta requirements"
  reported; clean stop) — its plan-stage consequence is the same stop;
  a non-empty-body bug run keeps skipping extraction and proceeding to a
  plan built from the issue itself (the flag is absent on the skip path,
  so the plan stage's stop check does not fire);
- the first-run corner keeps its skip-first ordering (a bug-labelled
  first run still never derives the full requirements set).

The suite pins both halves in the scenario's own test (the extract
stage's stop records the flag; the plan stage driven on the state the
extract stage left stops before its pi call, writes no plan file, and
records its skipped outcome line), the skip and standing-stop tests gain
their flag presences/absences, and the trigger-contract relay pin gains
the new key. The arc42 set (chapters 6, 7, 9) and the README's stage
bullets describe the signal as it now stands.
