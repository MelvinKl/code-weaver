# Issue #69 — Guard repairs by pi call, oracle reaches the extractor as a directory, planner gets the delta, tests reference their scenarios

**Summary**

One extraction delta, landed across eight of the fifteen oracle files, with
three coupled centrepieces. **(1) The shared guard stops being a git revert
plus a stage restart.** All three check sites (requirement-check,
plan-check, implement-check) keep their per-stage file sets and their one
shared implementation, but a violation is now *repaired with a pi call* — the
off-limits files named, told to be reverted, the stage's own work told to
stay valid against the task its initial instructions gave it — instead of the
guard reverting the files by git and the stage being re-run; the implement
stage's loop-back to the plan stage on a requirements-dir edit is removed
(repaired in place, the same call confirms the implementation's work is still
valid), and the loop cap now bounds the *repair calls* (capped repair runs
`MAX_LOOPS` times without clearing → the pipeline stops with a failure report
listing the violations). **(2) The extraction stage's context contract
re-slices the oracle.** The oracle no longer rides the extract call as an
expanded `@`-file list; the instructions name the requirements *directory*
as the oracle's location, list no requirement file by name, and pi reads the
files it judges relevant on demand (a directory is still never an
`@`-argument — the EISDIR pin survives in the successor scenario), while the
non-oracle sources (arc42 markdown, README, the baseline diff) stay the
call's `@`-file arguments. The plan stage is the flip side of the same
change: its instructions now *carry the delta* — which requirement files
changed and what those files changed — not just where the files are. A new
cross-cutting rule bounds the practice: a file list appears in a stage
instruction only where the set is the instruction's scope. **(3) The test
suite and the oracle link up.** Each test that implements a Gherkin scenario
carries a reference to the scenario it arose from (a correctness-only test
carries none), a run that changes a scenario in place pulls in the tests that
reference it (adjusted with it, fulfilling the requirement as it now reads),
and the review stage judges a changed test by the requirement it references.
The delta also lands the issue-#43 supersession that run #43 could not make
(`requirements/` was read-only to the extraction stage then): the
token-budget rewording now sits in the configuration, safety,
cost-and-token-usage and test-and-review files themselves, the "guard
re-run" loop is renamed "guard repair" across the oracle and the
documentation surfaces that repeat it, and the stale documented oracle counts
(156 stated vs 159 in the tree at this run's baseline — the suite's single
baseline-red test) must be recounted to the post-delta tree in this run.
