# Issue #98 — The job-timeout backstop becomes a target-side input, validated at trigger time

## Summary

Turn the factory's job-timeout backstop from a factory-side property (a
uniform `480`-minute `timeout-minutes` literal the workflow file declares on
its stage jobs, that no input of the reusable workflow sets) into a
**target-side input** — a `job-timeout` string input (default `"480"`
minutes) — the five stage jobs that make pi calls run under the target's
value as their job-level `timeout-minutes` (the trigger and setup-pi jobs
unaffected), and move the old "a declared pi call cap longer than the
backstop is clamped and the run records the exceedance" behaviour to a hard
**trigger-time failure**: the trigger stage validates the run's configuration —
a declared `job-timeout` that is not a number of minutes, or that does not
exceed the resolved pi call cap by at least the headroom the stage's
non-call work needs, fails the run at trigger time with a precise error and
no stage runs after the trigger — and lists the resolved job timeout in the
trigger's resolved-configuration record; the README's Inputs table documents
the new input, naming the runner that enforces it.

## Description

The delta is a **standing in-place change** to the existing
`requirements/configuration.feature` (the file predates the run's baseline;
the brownfield clause does not apply). In the job-timeout region of the file
it **deletes two scenarios and adds six**:

- **Deleted:** `A declared cap longer than the job's timeout backstop is not
  honoured` (the clamp-and-record-exceedance behaviour), and `The job's
  timeout backstop is a factory-side property` (the backstop is a factory
  property no input sets).
- **Added:** `A declared pi call cap the job timeout cannot exceed fails the
  run at trigger` · `The job's timeout backstop is a target-side input` ·
  `A non-numeric job timeout fails the run at trigger` · `A job timeout with
  no headroom over the resolved pi call cap fails the run at trigger` ·
  `The resolved job timeout rides the resolved-configuration record` · `The
  job timeout documentation names the runner that enforces it`.

Net, the requirements tree grows from **192 to 196 scenarios** (16 files
unchanged), while every documented surface still states 192 — the adjacent
existing scenario `requirement-extraction.feature::The documented oracle
counts match the requirements tree` goes red until step 6 updates the stated
counts.

Current state of the machinery (the gap the steps close):

- The backstop is factory-side today: the workflow file declares plain
  `timeout-minutes: 480` literals on the nine stage jobs that declare one
  (the trigger job declares no job-level timeout at all), no entry of the
  reusable workflow's input surface sets a job timeout, and the stage code
  knows the same value through the `JOB_TIMEOUT_MINUTES = 480` constant in
  the shared plumbing.
- The shared pi-call plumbing (`common.py`) resolves each call's cap through
  the documented chain (`INPUT_PI_TIMEOUT` → `CW_PI_TIMEOUT` → the 21600
  code default) and then **clamps** it to that backstop
  (`clamped_pi_timeout`), logging the exceedance in the job log of the
  stage that clamps; the trigger's resolved-configuration record block
  carries the matching **EXCEEDANCE branch** (it computes the declared
  `pi-timeout` against a `480`-minute literal in the same block).
- There is **no `job-timeout` input**, no trigger-time validation of the job
  timeout, no job-timeout line in the resolved-configuration record, and no
  arc42/README surface documents a job-timeout input. The **headroom**
  quantity the new scenarios name appears nowhere in the arc42 set today —
  undocumented, so the plan says so and plans around it (step 2): its value
  is derived, not invented — it is the margin the factory's own default pair
  already provides, 28800 seconds (the default 480-minute job timeout) minus
  21600 seconds (the documented default pi call cap) = **7200 seconds**,
  both anchors being documented input defaults.
- The five stage jobs that **make pi calls** are `extract`, `plan`,
  `implement`, `review` (the stages' generation calls, and the guard's
  repair call that rides their shared loop machinery) and `pr` (the
  PR-body call) — the chapter 6 shared-plumbing line names exactly those
  call families; the setup-pi job's smoke check is a pi call too, which is
  why the scenario's "unaffected" clause names the trigger and setup-pi
  jobs explicitly.
- The consumer workflow stays short and stable: it gains no `job-timeout`
  line (a consumer that leaves the input undeclared keeps the 480-minute
  backstop, so such a run is unchanged — the dogfood declares no
  `job-timeout` of its own).

## Acceptance Criteria

- **AC1** — `requirements/configuration.feature::The job's timeout backstop
  is a target-side input` (**adjusted** — it flips the baseline scenario
  `The job's timeout backstop is a factory-side property`, which the delta
  deletes in the same hunk): the reusable workflow declares `job-timeout`
  as a string input defaulting to `"480"` minutes; the five stage jobs that
  make pi calls run under the target's value as their job-level
  `timeout-minutes`; the trigger and setup-pi jobs are unaffected by the
  input; a consumer that leaves the input undeclared keeps the 480-minute
  backstop.
- **AC2** — `requirements/configuration.feature::A non-numeric job timeout
  fails the run at trigger` (**new**): a declared `job-timeout` value that
  is not a number of minutes fails the run at trigger time with a precise
  error; no stage runs after the trigger.
- **AC3** — `requirements/configuration.feature::A job timeout with no
  headroom over the resolved pi call cap fails the run at trigger`
  (**new**): where the declared job timeout does not exceed the resolved pi
  call cap (the target's declared `pi-timeout` value, or the 21600 default
  where undeclared) by at least the headroom the stage's own non-call work
  needs around each call, the run fails at trigger time with a precise
  error; no stage runs after the trigger.
- **AC4** — `requirements/configuration.feature::A declared pi call cap the
  job timeout cannot exceed fails the run at trigger` (**adjusted** — the
  successor of the deleted `A declared cap longer than the job's timeout
  backstop is not honoured`; the delta withdraws the clamp-and-record
  exceedance outcome and replaces it with a trigger-time failure): a
  declared `PI_TIMEOUT` longer than the job timeout minus the headroom
  fails the run at trigger time with a precise error, no stage runs after
  the trigger, and the trigger's record and the shared plumbing carry no
  exceedance-clamp behaviour any more. AC3 and AC4 are two views of the
  same inequality — one trigger-side validation discharges both.
- **AC5** — `requirements/configuration.feature::The resolved job timeout
  rides the resolved-configuration record` (**new** — a new entry on the
  existing record, whose workflow-log location and never-committed property
  are already pinned by the unchanged sibling scenario `The resolved pi call
  cap rides the resolved-configuration record`): the record lists the
  resolved job timeout (the declared value, or the `"480"` default) with the
  rest of the resolved configuration; the record stays in the workflow log,
  never committed to the repo.
- **AC6** — `requirements/configuration.feature::The job timeout
  documentation names the runner that enforces it` (**new** — the input did
  not exist at baseline, so no baseline scenario documents it): the
  `job-timeout` input's documentation for the target says the job timeout is
  enforced by whichever runner runs the job, and the target names that
  runner through the `runner` input.
- **AC7** — `requirements/requirement-extraction.feature::The documented
  oracle counts match the requirements tree` (**adjusted by this delta as a
  side effect**): the stated scenario count on every doc surface grows from
  192 to 196; the 16-file count is unchanged.

- [x] **2. Make the trigger stage validate the run's configuration at trigger
      time**
  - *Goal (AC2 new, AC3 new, AC4 adjusted — one validation discharges all
    three):* before the trigger records or accepts the run, it validates:
    (a) the resolved job timeout — the target's declared `job-timeout`
    value, or its `"480"` default — **is a number of minutes**, else the
    trigger fails with a precise error naming the offending value (AC2); and
    (b) the resolved job timeout **exceeds the resolved pi call cap** (the
    target's declared `pi-timeout` value, or the 21600 default where
    undeclared) **by at least the headroom** the stage's own non-call work
    (checkout, guard, loop machinery, artifact sync, push) needs around each
    call, else the trigger fails with a precise error naming both resolved
    values and the headroom (AC3; AC4 is the mirror of the same inequality —
    "a declared `PI_TIMEOUT` longer than the job timeout minus the
    headroom"). On failure the run fails at trigger time and no stage runs
    after the trigger — the same failure family as the trigger's existing
    pre-flight failures (`trigger.feature::A broken runner pre-requisite
    fails the trigger stage with a precise diagnosis`), and the downstream
    skip comes from the existing `needs:`/`started` gate. The default pair
    passes **at exactly the margin**: the factory's own defaults
    (28800-second job timeout, 21600-second cap) leave precisely the
    7200-second headroom, so a consumer that declares nothing validates and
    its run is unchanged.
