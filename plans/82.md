# Issue #82 — A target can add the pipeline step that installs the project's dependencies

**Summary**

Give a target project a way to declare — on its consumer workflow — the
pipeline step that installs the target project's own dependencies, so the
factory's stages that work the project (the implementation stage, the
test-and-review stage's suite) run against an environment where those
dependencies are installed; a target that declares no such step runs
unchanged, and the README plus the arc42 set document the mechanism.

**Description**

The delta is one **new** requirement file,
`requirements/project-dependencies.feature`, with four scenarios. The file
did not exist at the run's baseline, so **all four scenarios are new
requirements** — no existing scenario is adjusted by this delta, and no
standing test is edited on the requirement side. The mechanism the file
describes is currently undocumented and unimplemented: the pipeline installs
pi itself (stage 2) and configures the run's pi harness, but carries no step
that installs the target project's dependencies, and the README carries no
instructions for adding one.

The shape this plan implements:

- **Declaration channel** — one new *optional* workflow input
  (`dependency-install`, default empty) on the reusable workflow's
  `workflow_call` inputs. The consumer workflow (the only per-target code)
  declares the step by adding the input to its `with:` block. It is an
  input, not a secret: an install command is project configuration, and the
  documented harness-provider channel (secrets block → pi agent directory)
  belongs to the pi harness, not to the project's working environment.
- **Execution** — an inlined step in exactly the two stage jobs whose
  stages consume the dependencies (`implement` and `review`), placed after
  each job's checkout of the AI branch and before the job's stage script —
  so the declared step executes before the implementation stage and before
  the test-and-review stage's suite run, in each consuming job (each job's
  checkout replaces the workspace, so the install must run per consuming
  job, not once). The step reads the value through the documented
  `CW_<name>` env relay; where the value is empty the step is a no-op
  (logs, exits 0, touches nothing) — a target that declares no step runs
  unchanged: no dependency-install step runs, and the run's stages, pull
  request and final status report are unchanged by the mechanism's presence.
  No new stage job is added: the 15-stage / 9-job pipeline count, the
  self-contained inlined-steps shape, and the runtime-tree embedding are all
  preserved.
- **Documentation** — the README (Inputs table + the "Consume it (by ref)"
  example) and the arc42 chapters covering the same mechanism (4, 5, 6, 7,
  11) state the same thing: how to declare the step, that the run executes
  it before the stages that consume the dependencies, and that a target
  without one is unchanged. Knock-on: the new feature file grows the oracle
  tree to 16 files / 172 scenarios, so the stated oracle counts on the
  documented surfaces (README layout line + Requirements section, chapters
  1, 6, 11) must move with it — the standing `tests/test_oracle_counts.py`
  (unedited) is the test that enforces that consistency.

**Acceptance criteria**

- **AC1** — The factory exposes an optional declaration channel for a
  project-dependency-install step, and the run's pipeline executes the
  declared step as part of the run.
  *(Fulfilled by tasks 1 + 2; scenario: "The factory provides a way for a
  target to add a project-dependency-install step" — new.)*
- **AC2** — Where a target declares the step, it has executed before the
  factory's stages that consume the dependencies: the implementation stage
  and the test-and-review stage's suite run see the installed dependencies.
  *(Fulfilled by task 2; scenario: "The declared dependency-install step
  runs before the stages that consume the dependencies" — new.)*
- **AC3** — A target that declares no dependency-install step runs
  unchanged: no dependency-install step runs in the pipeline, and the
  run's stages, pull request and final status report are unchanged by the
  mechanism's presence.
  *(Fulfilled by task 2's no-op shape, held by task 4's regression run;
  scenario: "A target that declares no dependency-install step runs
  unchanged" — new.)*
- **AC4** — The README's instructions show how to declare the step the run's
  pipeline executes, and the arc42 documentation covering the same
  mechanism states the same; the documented oracle counts stay in sync with
  the grown tree.
  *(Fulfilled by task 3; scenario: "The README documents how to add the
  project-dependency-install step" — new, plus the standing oracle-count
  consistency the new file's arrival makes due.)*

**Tasks**

- [x] **Task 1 — Expose the declaration channel: one optional input the
  consumer's `with:` block passes, recorded in the trigger's resolved
  configuration.**

  1. *Goal and requirements.* Add the optional `dependency-install` input to
     the reusable workflow's `workflow_call` inputs (string, `required:
     false`, default empty — an older consumer's `with:` block stays
     schema-valid, exactly like the documented legacy `factory-ref`
     no-op), and have the trigger job's resolve step record the declaration
     (or its absence) in the run's resolved-configuration log line, the
     documented audit surface for resolved inputs. Fulfils **AC1 / scenario
     "The factory provides a way for a target to add a
     project-dependency-install step" (new)** — the factory-side half: the
     way to accept the declaration.
  2. *Test that proves it.* Add, in a new test module
     `tests/test_dependency_install_contract.py` (a new file the implement
     lane admits), a test whose docstring cites
     `requirements/project-dependencies.feature::The factory provides a way
     for a target to add a project-dependency-install step` (the machine
     citation form the test-reference convention prescribes) that checks,
     line-based on the workflow file (no whole-document YAML parse — the
     documented `on:`/YAML-1.1 gotcha): the input is declared under
     `workflow_call` inputs as optional with an empty default; the
     resolved-config log records the value (or the undeclared case); and the
     four harness providers on the `secrets:` block are untouched — the new
     channel is an input, and no secret value rides a `with:` input.
  3. *arc42 context.* Chapter 4 (the consumer workflow is the only
     per-target code — its `with:` inputs are where a target declares
     run-level settings) and chapter 8 (deployment view — the input surface
     and the harness-provider table). The chapter-3 constraint "secrets are
     never plain inputs" is honoured, not contradicted: the value is an
     install command, not a secret, so the input channel is the consistent
     one, and the four harness providers (the setup stage's materialisation
     into the pi agent directory) are deliberately not extended. The
     value's relay to the consuming stage jobs uses the documented
     `CW_<name>` step/job env idiom (chapter 3) or a direct input
     expression in the step's `env:`, and the trigger's resolved-config log
     keeps the audit complete (chapter 9: "the resolved configuration is
     recorded in the workflow log").

- [x] **Task 2 — Execute the declared step in the two consuming jobs, before
  their stages; make the step a no-op where the target declares nothing.**

  1. *Goal and requirements.* Add one inlined `dependency-install` step to
     each of the two stage jobs whose stages consume the project's
     dependencies — the `implement` job (stage 8) and the `review` job
     (stage 10, the `make test` suite run) — placed after the job's
     checkout of the AI branch and before the job's stage-script step (in
     `implement`, also before the stage-baseline recording, so the install's
     footprint is never counted as that stage's work by the guard). The step
     relays the input through the step's `env:` (`CW_DEPENDENCY_INSTALL:
     ${{ inputs.dependency-install }}`) and its body: where the value is
     empty it logs that no project-dependency-install step is declared and
     exits 0 without touching the workspace; where it is non-empty it runs
     the command in the checked-out workspace and a non-zero exit fails the
     job before the stage (the documented fail-explicitly idiom). No other
     job gains the step, and no new job is added. Fulfils **AC2 / scenario
     "The declared dependency-install step runs before the stages that
     consume the dependencies" (new)** and **AC3 / scenario "A target that
     declares no dependency-install step runs unchanged" (new)** (the no-op
     half; the "stages, pull request and final status report unchanged"
     half is held by the regression task below).
  2. *Test that proves it.* In the same new module, add two tests, each
     citing its scenario in the machine form: one for
     `requirements/project-dependencies.feature::The declared
     dependency-install step runs before the stages that consume the
     dependencies` asserting, line-based on the workflow file, that both the
     `implement` and the `review` job carry the step, and that in each the
     step's position is after the AI-branch checkout step and before that
     job's stage-script step ("Stage 8 — implement the plans …", "Stage
     10-11 — run the oracle, review, fix"); one for
     `requirements/project-dependencies.feature::A target that declares no
     dependency-install step runs unchanged` asserting the empty-value path
     is a no-op (the step body guards on the relayed value, logs the
     undeclared case and exits without touching the workspace) and that only
     those two jobs carry the step (every other job — trigger, setup-pi,
     baseline, extract, plan, pr, gates, report — is untouched, so the
     stages, PR and final status report are unchanged by the mechanism's
     presence).
  3. *arc42 context.* Chapter 5 (the pipeline is 9 jobs running 15 stages —
     both counts stay; "every stage's steps are inlined in the workflow
     file", so the new step is workflow-file text, not a new component).
     Chapter 7 (the per-job flow: each job stashes the runtime tree, reads
     the trigger state, checks out — the checkout *replaces the workspace*
     — then runs its stage; that is why the install must run in each
     consuming job after its own checkout, because a one-time install in one
     job's workspace cannot serve the next job's replaced workspace).
     Chapter 6 (self-contained/self-carrying: the step lives in the workflow
     file, not in the embedded runtime tree — so nothing in the runtime tree
     changes and the release flow's tree-freshness gate stays green; if the
     implementation touches a runtime-tree file anyway, `make embed`
     re-embeds it so the gate holds). The guard idiom is preserved: the
     install precedes the stage-baseline recording, and the implement guard's
     inverted allow shape (deny = requirements + plans; the current issue's
     plan re-allowed) is untouched.
