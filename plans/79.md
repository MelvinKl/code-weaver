# Issue #79 — Release flow: a consumer-workflow-only push must publish no release, and the release notes must name the real changes since the predecessor

**Summary:** Close the two holes a published release exposed in the automatic release
flow (`requirements/auto-release-on-main.feature`, issue-79 delta): (1) a push to
`main` whose only changed file is the consumer workflow
`.github/workflows/code-weaver.yml` changes nothing a published version carries
(a version is the factory workflow and its embedded runtime tree — never the
consumer's own workflow file), yet the flow spent a release number on it; such a
push must publish no release. (2) The release notes' "changed since" list was
always empty — the flow's checkout fetched a shallow history (its
`actions/checkout` step declares no fetch depth, so no tag is in the object
database), the range base fell back to "the first commit" even for a release with
a predecessor (which under a shallow fetch *is* HEAD itself, so the diff behind
it printed nothing), and the notes' diff was additionally pathspec-restricted to
a subset of the tree.

**Scope note.** The delta is confined to the changed requirement file
(`requirements/auto-release-on-main.feature` — the release flow's topic file;
files are structured by topic, never by issue, and house CI rejects
issue-named feature files, so no new feature file is created). The three new
scenarios and the one adjusted scenario live there and are already in the tree;
this plan implements the code, tests and documentation that fulfil them. Nothing
outside the implementation lane (requirements/ and plans/ are protected) is
touched by this plan's own writing — all edits below are work for the
implementation stage.

## Acceptance Criteria

- A push to main whose only changed file is the consumer workflow publishes no
  release — no new version tag, no new GitHub release, no version number spent —
  and a later push whose change set reaches the published version publishes the
  next release.
  → `requirements/auto-release-on-main.feature::A push that changes only the consumer workflow publishes no release`
  (**new** — no existing scenario covers the consumer-workflow-only skip)
- The release notes' changed-since reference is the predecessor release — not
  the first commit — and the notes list the files changed between the
  predecessor release and this release's commit.
  → `requirements/auto-release-on-main.feature::The release notes name the changes since the previous release`
  (**new**)
- The release notes' changed-since list is never empty for a release that
  publishes changes; the list names the files changed since the release's range
  base, and where the release has no predecessor its range base is the first
  commit and its list is still not empty.
  → `requirements/auto-release-on-main.feature::The release notes are never empty for a release that publishes changes`
  (**new**)
- A change on main whose files are **not** confined to the consumer workflow
  still automatically releases the next version.
  → `requirements/auto-release-on-main.feature::A change on main automatically releases a new version`
  (**adjusted** — the scenario gains the precondition "the change's files are
  not confined to the consumer workflow `.github/workflows/code-weaver.yml`";
  its When/Then are unchanged)

## Tasks

The implementation stage works this list top to bottom, flipping each box when
done. Tasks 1 and 2 edit the same self-contained workflow file and the same
contract-test module in sequence (the notes of a published release are
by-construction never those of a consumer-workflow-only push, so the skip must
exist first); task 3 records the final behaviour of 1–2 on the documentation
surfaces; task 4 is the small test-docstring consistency edit last.

- [x] **1. The release flow checks the push's changed files and publishes no
      release for a consumer-workflow-only push**

  1. *Goal and its requirements.* Fulfil the **new** requirement
     "A push that changes only the consumer workflow publishes no release"
     (`requirements/auto-release-on-main.feature`, `@issue-79`): a push to main
     whose changed files are **confined to the consumer workflow**
     (every changed file is `.github/workflows/code-weaver.yml`) creates no new
     version tag, publishes no new GitHub release and spends no version number;
     a later push whose change set reaches the published version publishes the
     next release.
     The scenario allows two mechanisms ("either the flow checks the push's
     changed files before publishing, or the trigger is adjusted so the change
     does not fire it"); this plan takes the **first** — a pre-publish check —
     because the trigger's shape ("fires on the main branch's advance") is
     pinned verbatim by the existing release-contract tests and by the
     chapter-8/README documentation surfaces, while a trigger change would
     force edits across those pinned surfaces.
     The skip predicate is the scenario's confinement wording exactly —
     *confined to the consumer workflow* — deliberately **not** generalised to
     "no changed file reaches a version file": the adjusted issue-21 scenario
     (task 4) requires that a change whose files are *not* confined to the
     consumer workflow still publishes, so a broader predicate would break it.
     The check applies to **push** events (`github.event.before` names the
     push's base commit; a push that creates the branch carries the zero sha —
     there the first commit is the base). A manual `workflow_dispatch` re-run is
     not a push: its no-op protection stays the documented one-tag-per-commit
     guard (a re-run at an unchanged HEAD publishes nothing —
     `requirements/reuse-by-ref.feature::Every published version is a stable
     ref`, which stays green untouched).
     Mechanism, in the release contract's documented idiom: a **new pure
     function and CLI shape in the documented shared-plumbing helper**
     `.github/scripts/release-number.py` (chapter 6 names it as the helper
     "the release workflow pipes … at run time"; the module's docstring
     already frames "three shapes, one rule" — the new shape is: changed-file
     names on stdin → **non-empty output is the skip signal**, mirroring the
     existing `--published-at` guard whose empty/non-empty distinction the
     workflow already reads). The workflow gains a **dedicated pre-publish
     step** (inlined in the self-contained file), placed after the documented
     embed-freshness gate and before the Publish step, so a skipped push exits
     cleanly — a green no-op like the existing guard — before any tag is
     created, pushed or released, and before a number is materialised. Keep
     the workflow's header comments accurate to its steps.
     Required consequence of the helper change: `release-number.py` is a member
     of the runtime tree embedded in `factory.yml` (the curated tree is
     `.github/scripts`, `.github/actions`, `pi-prompts`), so the PR must carry
     the documented `make embed` rewrite of `factory.yml` alongside it —
     otherwise the committed workflow carries a stale embedded tree and both the
     suite's embed contract test and the next release's publication gate ("a
     stale version is not published", chapters 6/8) fail.
  2. *The test that proves it.* **Add** unit tests to
     `tests/test_release_contract.py` (the module that unit-tests the helper's
     pure functions; each new test's docstring cites
     `requirements/auto-release-on-main.feature::A push that changes only the
     consumer workflow publishes no release` per the reference convention):
     change set confined to the consumer workflow → skip signal; a change set
     reaching a version file (the factory workflow or any file of the embedded
     runtime tree) → no skip; the consumer workflow **plus** at least one other
     file → no skip (the "not confined" half of the adjusted issue-21
     scenario); empty change set → no skip (an unchanged-HEAD re-run remains
     the one-tag-per-commit guard's case). **Add** a line-based workflow test
     in the same module (the module's documented idiom for the workflow file):
     `release.yml` runs the changed-files check as a pre-publish step and exits
     without publishing where the skip signal is non-empty — before any tag is
     created. The existing pinned lines stay true and their existing tests stay
     green unedited (the push event declares `main`; no tag trigger; no semver
     anywhere in the file; `git tag "$NEXT" HEAD`; `gh release create
     "$NEXT"`; the `contents: write` permissions block; the
     `GH_TOKEN: ${{ github.token }}` mapping; the tag-only push).
     `tests/test_embedded_runtime.py` (the embed contract test, unchanged)
     proves the accompanying `factory.yml` re-embed keeps the payload fresh.
  3. *arc42 context.* Chapter 4 (the consumer workflow is "the only per-target
     code" — never part of a version), chapters 6/8 (a version is the workflow
     file and its embedded runtime tree as one version; the flow's no-op guard
     discipline; the `make embed` rewrite committed by the maintainer, with the
     flow gating publication on its freshness), and chapter 6's shared-plumbing
     row (the helper the release workflow pipes into). **No contradiction with
     the arc42:** the flow's documented trigger is preserved as-is; the skip is
     the documented one-tag-per-commit no-op discipline extended to a push that
     changes nothing a version carries. The documentation surfaces that state
     "a push to main publishes the next version" unconditionally (chapter 8,
     README) must record the exception — that is task 3, a refinement, not a
     contradiction.

- [x] **2. The release notes take the predecessor release as their range base
      and list the real changes — never empty for a release that publishes
      changes**

  1. *Goal and its requirements.* Fulfil **two new** requirements
     (`requirements/auto-release-on-main.feature`, `@issue-79`):
     "The release notes name the changes since the previous release" — for a
     release with a predecessor, the notes' changed-since reference is the
     predecessor release, not the first commit, and the notes list the files
     changed between the predecessor release and this release's commit; and
     "The release notes are never empty for a release that publishes changes" —
     for a release published for a push that changed at least one file, the
     list is not empty and names the files changed since the range base; where
     the release has no predecessor, its range base is the first commit and its
     list is still not empty.
     Fixes in `.github/workflows/release.yml` (inlined steps, self-contained
     file):
     (a) **full history in the checkout** — configure the existing
     `actions/checkout` step to fetch full history (`fetch-depth: 0`). The
     arc42 is silent on the release flow's checkout fetch configuration — said
     so, and planned around: the factory workflow's own stage jobs already use
     `fetch-depth: 0` (the checkout idiom of `factory.yml`), so this brings the
     release flow's checkout in line with the repo's own documented convention;
     a separate `git fetch --tags` step would not restore the *real* first
     commit for the no-predecessor case, which a shallow clone reports as HEAD
     itself.
     (b) **the predecessor as range base, restricted to the new series** —
     compute the range base as the closest preceding **numbered** release:
     restrict `git describe` to the new scheme's tag shape (a bare integer —
     no `v` prefix, no dots; the scheme `release-number.py` defines, where the
     older `vX.Y.Z` tags "are not numbers" and "stay out of the series"), so an
     older semver tag can never name the reference. Where no numbered tag is
     reachable (a first release), the range base is the first commit — the
     notes' existing `${PREV:-the first commit}` dichotomy already encodes
     exactly the scenario's "predecessor release vs first commit" and is kept;
     only its computation changes.
     (c) **the list spans the whole tree** — remove the notes' diff
     pathspec restriction (`-- .github pi-prompts requirements`): a push that
     changes files elsewhere (docs, README, tests, …) publishes a release under
     task 1's predicate and would otherwise print an empty list, violating
     "never empty". Keep the diff between the range base and this release's
     commit in its stat-list form. A consumer-workflow-only push never reaches
     the notes at all — task 1 publishes no release for it.
     The Publish step's remaining behaviour is untouched: the number
     computation, the one-tag-per-commit guard, the tag on main's HEAD, the
     tag-object-only push, the tokenless `gh release create`.
  2. *The test that proves it.* **Add** to `tests/test_release_contract.py`
     (line-based per the module's idiom; docstrings cite the two new
     scenarios): for "The release notes name the changes since the previous
     release" — `release.yml` derives the range base from the predecessor
     release's tag restricted to the numbered series, references it in the
     notes (with the first-commit fallback only where no predecessor exists),
     and diffs the range base against this release's commit; for "The release
     notes are never empty for a release that publishes changes" — the checkout
     step fetches full history (tags in the object database for a release with
     a predecessor; the real first commit for a first release) and the notes'
     diff is not restricted to a path subset of the tree. The helper's existing
     pure-function unit tests (number series, one-tag-per-commit guard) are
     unchanged and stay green beside task 1's additions in the same module.
  3. *arc42 context.* Chapter 8 documents the flow's publication mechanics
     (tag on main's HEAD; tag-object-only push; default token; the "consumers:
     bump the ref" note) — all preserved; chapter 8 and the README must record
     the notes' new behaviour — task 3. The arc42 is silent on the checkout's
     fetch depth (stated in 1a; planned around via the repo's own
     `fetch-depth: 0` convention). **No contradiction with the arc42.**
