# 6. Building Block View

| Component | Path | Responsibility |
|---|---|---|
| Reusable workflow | `.github/workflows/factory.yml` | the 15-stage pipeline as 9 jobs (chapter 5); self-contained — every stage's steps are inlined in the workflow file (no composite actions to reference, no own-action ref), and self-carrying — the runtime tree its steps execute (the `.github` scripts, the stage scripts, the pi prompt templates) is embedded in the file as a base64 tarball: stage 1 materialises it into `$RUNNER_TEMP` before the first checkout replaces the workspace, and the trigger's artifact carries it to every later stage job's first step — so the ref on the consumer's `uses:` line is the only version selection a run makes, and no run fetches the factory repo (the factory project's own repo pins the public release line too — a run triggered in it checks and works the triggered repo's own code while the machinery is the pinned tag's version, the dogfood exercising the published line; chapter 8) |
| Consumer workflow (per target) | `.github/workflows/code-weaver.yml` | short & stable: an external target pins the factory by owner, repo, path and a version tag (never a moving branch) — one pin: the file carries its runtime tree embedded, so no second ref accompanies it; this repo is the factory project itself, and its workflow pins the public release line — a version tag of the MelvinKl line — with the (legacy) `factory-ref` input left undeclared (no stage reads it anymore; the dogfood thereby exercises the published version its external targets get, while a run triggered in it checks and works the code of the repo it was triggered in; chapter 8); `with:` inputs, `GH_TOKEN` (the only required secret) plus the four optional harness-provider secrets (`PI_MODELS`, `PI_SETTINGS`, `PI_MCP`, `PI_EXTENSION_ENV`) via `secrets:`, the `labeled`-only issue trigger + manual dispatch |
| trigger | `factory.yml` `trigger` job | fetch the issue; gate on the trigger label or manual dispatch; record issue number/title/body + the run baseline (ref + change-set diff) as state; idempotency lock on in-progress runs |
| setup-pi | its steps are inlined in `factory.yml`; its script `.github/actions/setup-pi/` | installs pi for the run (into the agent directory — every later pi invocation in the run resolves that installed copy) and configures it for the workflow run: resolve each harness provider (a non-empty GitHub secret wins over the named repo file — the model configuration, the additional packages, the MCP configuration, the extension's environment) → write the harness into the agent directory the invocation resolves (`~/.pi/agent/`, or `PI_CODING_AGENT_DIR` — the runner's pre-existing user-level configuration is replaced for the run, never read as the run's; no pre-installed or pre-configured pi is a pre-requisite of the runner environment) → backend reachability (the configuration the stage wrote — a provided file without an OpenAI-compatible backend URL fails "no backend in the provided configuration") → model in the written set → headless `pi --print` smoke check of the installed pi; an install or configuration that cannot complete fails the stage explicitly, no later stage runs |
| baseline | its steps are inlined in `factory.yml`; its script `.github/actions/baseline/` | cut `ai/code-weaver/<n>` at the target's head (reuse the branch when it exists); record `baseline.sha` + `baseline.diff` as state |
| extract-stage | its steps are inlined in `factory.yml`; its script `.github/actions/extract-stage/` | stages 4+5: pi derives the delta Gherkin — **its context is the `@`-file slice** (oracle + arc42 markdown + `README.md` + the baseline diff, handed to pi as `@`-file arguments; pi reads the named files as context before answering); the prompt tolerates arc42 structure variance (proceeds on the readable parts) and **places the delta by topic — extending the existing topic file, creating a new file only for a topic no file yet covers, never one named after the issue**; the guard keeps the delta inside the requirements dir, a changed existing file that no longer parses is reverted and the stage re-runs |
| plan-stage | its steps are inlined in `factory.yml`; its script `.github/actions/plan-stage/` | stages 6+7: one Jira-ticket-style plan per issue at `plans/<n>.md`; the planner's context = the changed requirements + the arc42 markdown (`docs/` files — the top-level `PLAN.md` where a target has no doc dir) + the README, referenced by path (the path-referenced slice) |
| implement-stage | its steps are inlined in `factory.yml`; its script `.github/actions/implement-stage/` | stages 8+9: works the plan one open task at a time (the plan is a live state tracker, injected in full as the one `@`-file); keep the arc42 set complete, the README current; the guard runs inverted — the implementation's lane is everything except the protected set (requirements and the plans dir), with exactly the current issue's plan file re-allowed over it (another issue's plan is a reverted violation; a brand-new `tests/` dir or docs set the implementation creates is admitted, never reverted); a requirement edit loops back to stage 6 |
| review-stage | its steps are inlined in `factory.yml`; its script `.github/actions/review-stage/` | stages 10+11: run the target's suite (`make test` → the stdlib-only runner) — the suite executes every scenario; pi judges only the Scenarios of the feature files this run changed against the output (the review call's context is path-referenced — test output + the changed feature files; a run that changed no requirements passes vacuously); the per-scenario verdict block is the oracle; the fix loop is bounded; per-iteration logs go to the state dir (artifact), never the tree |
| pr-open | its steps are inlined in `factory.yml`; its script `.github/actions/pr-open/` | stage 12: push the AI branch; open (or update) the PR `ai/<n>` → `target-branch`; the **PR body is generated by pi** (`pi-prompts/pr-body.md` via the `pi-run` action) **from the requirements, the plan and the review — and it describes the issue the run implements** (what the issue asked for, the plan it built, which scenarios changed, the review verdicts); the template assembler builds the same description as the fallback when the pi call produces nothing — the issue's number and title read from the trigger's state files (the authoritative channel where the job-env relay drops them), the issue's plan embedded, the run's changed scenarios listed — and no resolved-configuration dump (that lives in the workflow log) |
| gates-stage | its steps are inlined in `factory.yml`; its script `.github/actions/gates-stage/` | stages 13+14: poll every PR-triggered workflow until green; fix red gates and re-poll, bounded; **no merge call exists** |
| report | its steps are inlined in `factory.yml`; its script `.github/actions/report/` | stage 15: complete the PR body (the final status report) — listing the run's usage totals (total input tokens, total output tokens, total cost) assembled from the per-call usage records in the state dir (a state file that travels with the run's state artifacts like every other stage value: each stage's artifact carries the cumulative ledger, so the totals cover every pi call the run made, and a stage that never ran contributes nothing) — the cost derived from that recorded usage, keyed on the run's resolved `llm-model`, with the rates used listed — the rates are the resolved model's `cost` entry in the run's model configuration (the provider the setup stage materialises: a non-empty `PI_MODELS` secret wins over the repo file `.pi/agent/models.json`; the report lists the source it read the rates from), a model with no cost entry is listed as unpriced (— chapter 10). The stage re-reads the PR after editing its body and keeps the pointer comment ("final status is in the PR body") only where the completion verified; where it could not be applied — the PR was already merged, or the edit was refused on both write paths (the `gh pr edit` GraphQL mutation and a REST `PATCH /pulls/{n}` fallback) — the comment carries the full final status itself, so the PR description and the issue comment never disagree on the run's numbers. The source issue is commented and closed with the completed state reason when the run succeeded (a failed run leaves it open for a re-trigger; the close is best-effort — a refusal is warned, never fatal); append the **AI-activity section to the arc42 markdown** — the first file under `doc-dir`, falling back to the top-level `PLAN.md` where a target has no doc dir (chapter 1 carries it in this repo). The inlined status-report step acquires the plumbing names its body calls by bare name (the state dir, the state file, the log, the gh api, the branch push) on two paths: where the shared module resolves from the runtime tree the job stashed to `$RUNNER_TEMP`, the step's `import common` binds them to the shared module's definitions for the body; where it does not resolve (a consumer pinned to a factory ref that predates the module, the legacy workspace-copy tree, a runner build whose stashed path breaks the import resolution), the step's `ImportError` branch binds the same names to local fallback definitions in the step — an extension of the self-contained, pinned-refs-keep-working mechanism (chapter 8), the body's calls unchanged, only how the names are bound differing — and the two paths are behaviourally equivalent for the report's output (one ledger, one set of numbers on both the PR body and the issue comment) |
| pi-run | its steps are inlined in `factory.yml`; its script `.github/actions/pi-run/` | the declarative headless primitive: `pi --print --mode json --model <m>` — instructions folded into the user text, context referenced by path, the plan files injected in full; records the call's input & output token usage in the run's usage ledger (the state-dir file that travels with the artifacts) as the call finishes |
| shared plumbing | `.github/scripts/common.py`, `stages.py`, `gherkin-validate.py`, `release-number.py` | state dir, loop caps, the guard, `pi_invoke` (the two context slices; each finished call appends its input & output token counts as one usage-record line to the `tokens.txt` ledger in the state dir — a call that left no usage record appends nothing), crash diagnostics, the official-parser Gherkin validator (**skipped-not-failed** where the parser port is absent), the shared bounded loop machinery, the release tag's next single increasing number (`release-number.py`; the release workflow pipes the remote's tag list into it at run time) |
| prompt templates | `pi-prompts/{requirements,plan,implement,review,pr-body}.md` | the stage instructions (handed to pi as user text — pi's default system prompt stays in place; the thinking level is never pinned — pi-jev chooses it per prompt) |
| oracle | `requirements/` (15 files, 156 scenarios) | the Gherkin requirements the implementation must fulfil |
| arc42 set | `docs/01…11-*.md` | this documentation — one chapter per file; chapter 1 carries the AI-activity section the report stage appends to |
| tests | `tests/run.py` (stdlib-only runner) + `tests/test_*.py` | the validator's unit tests, the stream-capture tests, the trigger-contract tests, the stage-contract tests, and the release-contract tests; auto-discovered by the stdlib runner and by pytest alike |
