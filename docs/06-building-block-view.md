# 6. Building Block View

| Component | Path | Responsibility |
|---|---|---|
| Reusable workflow | `.github/workflows/factory.yml` | the 15-stage pipeline as 9 jobs (chapter 5) — the five stage jobs that make pi calls run under the target's `job-timeout` input — default `480` minutes — as their job-level `timeout-minutes` (a consumer that leaves the input undeclared keeps the 480-minute backstop, so its run is unchanged; the trigger and the setup-pi jobs are unaffected by the input; the stage code knows the same value through the shared plumbing); self-contained — every stage's steps are inlined in the workflow file (no composite actions to reference, no own-action ref), and self-carrying — the runtime tree its steps execute (the `.github` scripts, the stage scripts, the pi prompt templates) is not embedded in the file: stage 1 fetches the called version's runtime tree at the called ref — recovered from the consumer workflow, never relayed as a second pin — into `$RUNNER_TEMP` before the first checkout, and the trigger's artifact carries it to every later stage job's first step — so the ref on the consumer's `uses:` line is the only version selection a run makes, and the ref's published version carries the file and the tree together — the version's shape the release flow's publication gate keeps consistent (`.github/scripts/embed-runtime.py`'s `--check`, the flow's pre-tag step: the committed file plain text within the max allowed size, the tagged commit's tree carrying the runtime tree the file's stage steps execute — a version that is not consistent is never tagged) (the factory project's own repo pins the public release line too — a run triggered in it checks and works the triggered repo's own code while the machinery is the pinned tag's version, the dogfood exercising the published line; chapter 8); its input surface also carries the optional `dependency-install` input — the command the run's pipeline runs to install the target project's dependencies, executed in the `implement` and `review` jobs after each job's checkout and before its stage; empty = no such step, the run is unchanged; the optional `dependency-upgrade` setting (the setting's default is `on`; `off` = the pipeline runs without the stage — the run's stages, pull request and final status report are unchanged by the upgrade's absence) decides whether the run's pipeline runs the dependency-upgrade stage — the stage upgrades the project's dependencies to newer versions, before the implementation stage, as an inlined step in the `implement` job; the optional `auto-update` setting (the setting's default is `true`; `off` = the pipeline runs without the stage — the run's stages, pull request and final status report are unchanged by the stage's absence) decides whether the run's pipeline runs the update stage — the stage updates every requirement in the oracle to its newest version, between the requirement-extraction and the planning stages, as an inlined step in the `plan` job; the optional `pi-timeout` input (the input's default is `21600` — the current 360-minute cap; a target that leaves it undeclared runs unchanged under that cap) sets the per-call time cap every pi invocation in the pipeline runs under — a declared value that leaves the stage's non-call work no headroom fails the run at trigger time with a precise error, and no stage runs after the trigger (the trigger validates the resolved job timeout against the resolved cap plus the headroom — chapters 5 and 7); a run that reaches a stage has validated the pair, and its pi calls honour the declared value; the chain the cap resolves through is named in the shared-plumbing line; the optional `fastmode-threshold` input (the default `5` steps; a consumer that leaves it undeclared keeps the default, its run unchanged) — the plan's step count below which the implement stage works every open step in a single iteration, a plan at or above it keeping the one-step-at-a-time loop (the implement-stage line; no trigger-time validation guards the input — a declared value that is not an integer number of steps is skipped for the 5-step code default where the implement stage resolves it) |
| Consumer workflow (per target) | `.github/workflows/code-weaver.yml` | short & stable: an external target pins the factory by owner, repo, path and a version tag (never a moving branch) — one pin: the ref selects the published version, so no second ref accompanies it; this repo is the factory project itself, and its workflow pins the public release line — a version tag of the MelvinKl line — with the (legacy) `factory-ref` input left undeclared (no stage reads it anymore; the dogfood thereby exercises the published version its external targets get, while a run triggered in it checks and works the code of the repo it was triggered in; chapter 8); `with:` inputs (the optional `dependency-install` input — the target's dependency-install command; undeclared = the run is unchanged; the optional `dependency-upgrade` setting — whether the run's pipeline runs the dependency-upgrade stage: the stage upgrades the project's dependencies to newer versions, before the implementation stage; the setting's default is `on`, and a target turns it off with a `dependency-upgrade: off` line in the `with:` block, like `max-loops` — `off` = the pipeline runs without the stage, the run is unchanged by the upgrade's absence; the optional `auto-update` setting — whether the run's pipeline runs the update stage: the stage updates every requirement in the oracle to its newest version, between the requirement-extraction and the planning stages; the setting's default is `true`, and a target turns it off with an `auto-update: off` line in the `with:` block, like `max-loops` — `off` = the pipeline runs without the stage, the run is unchanged by the stage's absence), `GH_TOKEN` (the only required secret) plus the four optional harness-provider secrets (`PI_MODELS`, `PI_SETTINGS`, `PI_MCP`, `EXTENSION_ENV`) via `secrets:`, the `labeled`-only issue trigger + manual dispatch |
| trigger | `factory.yml` `trigger` job | fetch the issue; gate on the trigger label or manual dispatch; record issue number/title/body + the run baseline (ref + change-set diff) + the bug-issue flag — the issue's labels compared against the resolved bug label (the `bug-label` input's value, its `bug` default where the consumer leaves the input undeclared) — as state (the flag is recorded, never gated on: the trigger label, or a manual dispatch, starts the run, an issue carrying only the bug label starts no factory; the flag rides the trigger's artifact to every later stage job, whose Read trigger state step relays it into the job's env); idempotency lock on in-progress runs |
| setup-pi | its steps are inlined in `factory.yml`; its script `.github/actions/setup-pi/` | installs pi for the run (into the agent directory — every later pi invocation in the run resolves that installed copy) and configures it for the workflow run: resolve each harness provider (a non-empty GitHub secret wins over the named repo file — the model configuration, the additional packages, the MCP configuration, the extension's environment) → write the harness into the agent directory the invocation resolves (`~/.pi/agent/`, or `PI_CODING_AGENT_DIR` — the runner's pre-existing user-level configuration is replaced for the run, never read as the run's; no pre-installed or pre-configured pi is a pre-requisite of the runner environment) → backend reachability (the configuration the stage wrote — a provided file without an OpenAI-compatible backend URL fails "no backend in the provided configuration") → model in the written set → headless `pi --print` smoke check of the installed pi; an install or configuration that cannot complete fails the stage explicitly, no later stage runs |
| baseline | its steps are inlined in `factory.yml`; its script `.github/actions/baseline/` | cut `ai/code-weaver/<n>` at the target's head (reuse the branch when it exists); record `baseline.sha` + `baseline.diff` as state |
| extract-stage | its steps are inlined in `factory.yml`; its script `.github/actions/extract-stage/` | stages 4+5: pi derives the delta Gherkin — **its context is the `@`-file slice** (the arc42 markdown + `README.md` + the baseline diff, handed to pi as `@`-file arguments; pi reads the named files as context before answering) plus the oracle's reach — the requirements directory named in the instructions, no requirement file listed by name, pi reading the files it judges relevant from that directory on demand (a directory is never an `@`-argument); a run for an issue that carries the resolved bug label (the trigger records the bug-issue flag in the run's state) skips the derivation entirely — the entry logic's first branch, checked before the directory branch: no pi call is made for the stage, no requirement file is written, the requirement check passes with no requirement file changed (the guard's whitelist over the requirements dir is trivially satisfied — no file is touched, so no repair call), the stage records its skip on the stage-summary channel (never as `stage complete`), and the run proceeds to the update stage (when the AUTO_UPDATE setting runs it) and then to the planning stage (the plan is built from the issue itself; the 15-stage / 9-job shape is unchanged — the skip is a recorded outcome inside the existing job, not a new stage or job), while a bug-labelled issue with an empty body instead reaches the `no delta requirements` clean stop: the stop records its run-level half — the `no-delta-stop` flag in the run's state dir beside the trigger's recorded state (it rides the cumulative artefact chain to every later stage job, and the per-job env relay, like the other trigger-state keys) — which the update stage (its step) and the plan stage check before their own work: set, the plan stage stops cleanly without a pi call (no plan file, its own outcome line the report renders as skipped, never as `stage complete`), so the run is not forwarded to the update stage or the plan stage; the skip itself records no flag (the bug-labelled run's way through to the plan); the entry logic then branches on whether the target has a requirements directory — **present**: the standing delta behaviour, the empty/missing-issue-body stop (no requirement file written; the factory reports `no delta requirements` and stops cleanly — the standing stop records the same `no-delta-stop` flag, so a run that stops there is not forwarded to the update stage or the plan stage either) applying only where the directory exists; **absent**: a first factory run on that project — the stage takes its first-run branch instead of stopping, and the full-derivation prompt has pi derive the project's **full** requirement set from its current code, documentation and tests (a source the project does not have is skipped rather than failing, the skipped-not-failed structure-variance tolerance generalised from arc42 chapters to sources), written as `.feature` files that **create** the requirements directory, placed by topic (every topic file a new one, since no file covers a topic yet — the code and test trees are reached by pi's read tool on demand, never `@`-arguments, so the two-slice context contract stands unchanged); the prompt tolerates arc42 structure variance (proceeds on the readable parts) and **places the delta by topic — extending the existing topic file, creating a new file only for a topic no file yet covers, never one named after the issue**; the guard keeps the delta inside the requirements dir, a changed existing file that no longer parses is reverted and the stage re-runs; at its completion points the shared loop pushes the AI branch — the stage's committed work is on the remote before the run proceeds (the job-tail push step stays as the job's final sync) |
| update-stage | its step is inlined in the `plan` job; its script `.github/actions/update-stage/` | the optional stage between the requirement-extraction and the planning stages — the `AUTO_UPDATE` setting (the workflow's optional `auto-update` input, its `true` default; the trigger records the resolved value as a state file in its recorded run state, and the plan job's Read trigger state step relays it into the job's env like the other trigger-state keys) gates it: **on**, the stage updates every requirement in the oracle to its newest version — a scenario that no longer holds against the project's current state is updated in place (the oracle is the single source of truth — the documented in-place-update idiom), a requirement already at its newest version — including the ones this run's extraction just derived — is left untouched (the update's footprint never disturbs the run's delta the plan stage covers), and a Gherkin requirement that prohibits a requirement from being updated leaves that requirement at its current version; **off**, the step is a no-op (it guards on the setting, logs and exits before its stage-baseline recording): the pipeline runs without the stage — no other job gains a step, and the run's stages, pull request and final status report are unchanged by the stage's absence (the documented dependency-upgrade off-form); a run whose extraction stopped with the `no-delta-stop` flag gets the step no-op'ing too — the run that stopped at the extraction is not forwarded to the update stage, its documented clean-stop outcome undisturbed. Placed after the job's checkout of the AI branch and before the plan stage step and its stage-baseline recording (the plan stage's baseline re-records the branch tip after the step), the update's footprint is never counted as the plan stage's work by the guard; the step's pi call runs under the plan job's documented `job-timeout`; its context is the path-referenced slice — the arc42 set and the README referenced by path, the requirements directory named as the oracle's location, pi reading the files it judges relevant on demand (a directory is never an `@`-argument); its guard runs the shared idiom with the requirements directory as the lane (a change outside it is reverted in place by the guard's pi call); its validation is the documented extraction validation (a changed feature file that no longer parses is reverted and the stage re-runs, the parser's complaint carried back into the next attempt); at its completion points the shared loop commits the stage's work and pushes the AI branch — the push fires only after the guard has passed; the stage records its outcome on the stage-summary channel (a done stage reported `stage complete`, the report's stage-outcome list rendering from it) |
| plan-stage | its steps are inlined in `factory.yml`; its script `.github/actions/plan-stage/` | stages 6+7: the job also runs the optional update stage as an inlined step before the plan stage step (its step checks the run's `no-delta-stop` flag and no-ops — the run that stopped at the extraction is not forwarded to the update stage, its documented clean-stop outcome undisturbed — and the AUTO_UPDATE setting gates it like the documented dependency-upgrade off-form); one Jira-ticket-style plan per issue at `plans/<n>.md`; before any prompt assembly the stage checks the run's `no-delta-stop` flag (the extract stage records it in the run's state dir when it takes the no-delta stop — a bug-labelled issue with an empty body, or the standing empty-body stop — beside the trigger's recorded state, riding the cumulative artefact chain to every later stage job, the per-job env relay in-process, like the other trigger-state keys): set, the run is not forwarded to the plan stage — the stage stops cleanly without a pi call — no plan file, no prompt assembly (the bug branch's empty-body form, which would plan from the issue title alone, is never reached) — and records its own outcome line on the stage-summary channel, which the report renders as skipped, never as `stage complete`; a bug-labelled run whose extraction merely skipped records no flag and proceeds to the prompt assembly; the planner's instructions carry the delta — which requirement files changed since the baseline and what those files changed (the run's baseline diff scoped to them — the baseline the plan stage records re-records the branch tip after the job's update step, so the update's footprint is never counted as the plan stage's work by the guard) — and, where the run's delta is the **brownfield shape** (every changed requirement file *new* against the baseline — the extraction created the requirements directory, so the baseline knows none of them), the instructions attach the brownfield clause: the requirements were extracted from the project's existing code, the plan names the extracted scenarios it must cover, its steps are scoped to adjusting the tests to reference those scenarios, and no plan step implements code (a delta that changes an existing file — the standing runs — is not that shape, and the clause is not attached) — and, where the run's issue is a bug issue (the trigger's recorded bug-issue flag) and no requirement file changed since the baseline — the run skipped the extraction for it — the instructions take the empty-delta branch: they name no requirement file as changed and carry the issue itself — its number, title and body — as what the plan must cover (the issue data rides the trigger's state files — the channel the pr-open line documents as the authoritative one for the issue's number and title — plus the body file the extract stage reads; a body the trigger did not record is carried as empty, the plan still built from the number and title; and the brownfield clause is not attached to this shape — a bug run's delta is empty, no files at all, unlike the all-new-file shape) — and the planner's context = those changed requirements + the arc42 markdown (`docs/` files — the top-level `PLAN.md` where a target has no doc dir) + the README, referenced by path (the path-referenced slice; pi reads the changed files on demand, and the whole existing oracle is not injected into the planner); the guard verifies only that one plan file changed — any other change is reverted by the guard's pi call and the plan stage re-runs its generation on the guard's cleared-repair record (the guard re-checks the re-run; a clean plan stage completes without re-running), while the extract and implement checks complete without re-running; at its completion points the shared loop pushes the AI branch — the stage's committed plan is on the remote before the run proceeds (the job-tail push step stays as the job's final sync) |
| implement-stage | its steps are inlined in `factory.yml`; its script `.github/actions/implement-stage/` | stages 8+9: the plan is a live state tracker, injected in full as the one `@`-file — and the resolved fastmode threshold (the workflow's `fastmode-threshold` input through the documented settings chain, the 5-step default where the consumer leaves it undeclared) branches how the stage works it: **at or above** the threshold the stage works the plan one open step at a time — each completed step's changes are committed on the AI branch and the branch is pushed before the next step starts: the per-step commit-and-push is the durability half of the one-step-at-a-time contract, a run terminated after a step's push keeps the completed step's work on the remote branch, and a re-triggered run finds the step still marked done in the plan file; **below** it a single iteration works every open step of the plan (the implement template's fastmode clause names the mode, the target instructions list the open steps the call works) — every step marked done in the plan file when the call finishes, the stage runs no further per-step iteration for the plan, and the shared loop's completion point commits and pushes the work, the single-iteration mode's durability point (there is no 'next step' to push before): a run terminated after that push keeps the work on the remote branch, and a re-triggered run finds every step done and exits as the satisfied no-op — keep the arc42 set complete, the README current; where the plan is a brownfield plan (its steps all scope to adjusting the tests to reference the extracted scenarios, none implements code — the plan stage's brownfield scope makes the plan read that way), the run adjusts the tests without implementing code: the implementation changes **no source code** — the changed files are the tests and the issue's plan file — and adjusts the existing tests to reference the requirements they describe, the docstring citation convention applied to the *adjusted* tests — no guard change serves this: the inverted allow already admits the brownfield change set, so the no-source-code scope is enforced by the plan's step scope plus the prompt clause and verified by the review stage, which already judges a changed test by the requirement it references (on a brownfield target that is exactly the acceptance path for the adjusted tests); a generated test that implements a Gherkin scenario cites it in its docstring as `<feature file>::<scenario name>` (a test that is only for correctness carries no such reference), and a scenario changed in place pulls in the tests that cite it; the guard runs inverted — the implementation's lane is everything except the protected set (requirements and the plans dir), with exactly the current issue's plan file re-allowed over it (another issue's plan is a violation the guard repairs with a pi call; a brand-new `tests/` dir or docs set the implementation creates is admitted, never reverted); a requirement edit is repaired in place — the guard's pi call reverts it and confirms the implementation's work stays valid — the stage is not re-run and does not loop back to stage 6 |
| review-stage | its steps are inlined in `factory.yml`; its script `.github/actions/review-stage/` | stages 10+11: run the target's suite (`make test` → the stdlib-only runner) — the suite executes every scenario; pi judges the Scenarios of the feature files this run changed, plus the scenarios the run's changed tests reference (extracted from their docstrings — a changed test is judged by the requirement it references), against the output (the review call's context is path-referenced — test output + the changed feature files + the run's changed test files; a run that changed no requirements and no referencing tests passes vacuously); the review runs on every iteration's output (red or green) and its full output — the reviewer's report — is mirrored per iteration into the state dir: the fix directive names it by path and the fixer reads it on demand (a red iteration whose review breaks keeps the fix loop running on the raw output; on a green suite the same breakdown fails the stage); the per-scenario verdict block is the oracle; the fix loop is bounded and pushes the AI branch after each fix commit (the branch is the documented cross-job channel), and at the stage's completion point (the suite green and every in-scope scenario fulfilled — or the vacuous empty-delta pass) the stage pushes the branch: a no-op in the normal case, its fix iterations already pushing — the push-at-completion guarantee made explicit and uniform; per-iteration logs go to the state dir (artifact), never the tree |
| pr-open | its steps are inlined in `factory.yml`; its script `.github/actions/pr-open/` | stage 12: push the AI branch; open (or update) the PR `ai/<n>` → `target-branch`; the **PR body is generated by pi** (`pi-prompts/pr-body.md` via the `pi-run` action) **from the requirements, the plan and the review — and it describes the issue the run implements** (what the issue asked for, the plan it built, which scenarios changed, the review verdicts); the template assembler builds the same description as the fallback when the pi call produces nothing — the issue's number and title read from the trigger's state files (the authoritative channel where the job-env relay drops them), the issue's plan embedded, the run's changed scenarios listed — and no resolved-configuration dump (that lives in the workflow log) |
| gates-stage | its steps are inlined in `factory.yml`; its script `.github/actions/gates-stage/` | stages 13+14: poll every PR-triggered workflow until green; fix red gates and re-poll, bounded; **no merge call exists** |
| report | its steps are inlined in `factory.yml`; its script `.github/actions/report/` | stage 15: complete the PR body (the final status report) — the stage outcomes it lists render from the stages' recorded summary lines: a stage that is done is reported "stage complete" (its per-step lines stay out of the outcome), a stage whose work was intentionally skipped — the extract stage on a bug-labelled run (whose skip its bug-skip branch records on this channel), the update stage on a run whose extraction stopped with no delta (whose skip line its no-delta-stop gate records on this channel), or the plan stage on a run whose extraction stopped with no delta (whose stop line its no-delta-stop gate records on this channel) — is listed as skipped, never as "stage complete" (a stage that did no work is not a done stage; a completion line it recorded alongside stays out of the outcome), and a stage that will re-run — the implement stage's per-step "step <k>/<n> done" lines recorded on the stage-summary channel without a completion line — is reported per step for each of its finished steps — listing the run's usage totals (total input tokens, total output tokens, total cost) assembled from the per-call usage records in the state dir (a state file that travels with the run's state artifacts like every other stage value: each stage's artifact carries the cumulative ledger, so the totals cover every pi call the run made, and a stage that never ran contributes nothing) — the cost derived from that recorded usage, keyed on the run's resolved `llm-model`, with the rates used listed — the rates are the resolved model's `cost` entry in the run's model configuration (the provider the setup stage materialises: a non-empty `PI_MODELS` secret wins over the repo file `.pi/agent/models.json`; the report lists the source it read the rates from), a model with no cost entry is listed as unpriced (— chapter 10). The stage re-reads the PR after editing its body and keeps the pointer comment ("final status is in the PR body") only where the completion verified; where it could not be applied — the PR was already merged, or the edit was refused on both write paths (the `gh pr edit` GraphQL mutation and a REST `PATCH /pulls/{n}` fallback) — the comment carries the full final status itself, so the PR description and the issue comment never disagree on the run's numbers. The source issue is commented and closed with the completed state reason when the run succeeded (a failed run leaves it open for a re-trigger; the close is best-effort — a refusal is warned, never fatal); append the **AI-activity section to the arc42 markdown** — the first file under `doc-dir`, falling back to the top-level `PLAN.md` where a target has no doc dir (chapter 1 carries it in this repo). The inlined status-report step acquires the plumbing names its body calls by bare name (the state dir, the state file, the log, the gh api, the branch push) on two paths: where the shared module resolves from the runtime tree the job stashed to `$RUNNER_TEMP`, the step's `import common` binds them to the shared module's definitions for the body; where it does not resolve (a consumer pinned to a factory ref that predates the module, the legacy workspace-copy tree, a runner build whose stashed path breaks the import resolution), the step's `ImportError` branch binds the same names to local fallback definitions in the step — an extension of the self-contained, pinned-refs-keep-working mechanism (chapter 8), the body's calls unchanged, only how the names are bound differing — and the two paths are behaviourally equivalent for the report's output (one ledger, one set of numbers on both the PR body and the issue comment) |
| pi-run | its steps are inlined in `factory.yml`; its script `.github/actions/pi-run/` | the declarative headless primitive: `pi --print --mode json --model <m>` — instructions folded into the user text, context referenced by path, the plan files injected in full; records the call's input & output token usage in the run's usage ledger (the state-dir file that travels with the artifacts) as the call finishes |
| shared plumbing | `.github/scripts/common.py`, `stages.py`, `gherkin-validate.py`, `release-number.py` | state dir, loop caps, the guard (its violation repair is a pi call through `pi_invoke` — the repair instructions are assembled in the plumbing as a state-dir file the call reads, so the `pi-prompts/` template count stays six, one per pi-calling stage — and each finished repair call appends its token usage to the ledger like every other call), `pi_invoke` (the two context slices, the per-call time cap resolved through the documented chain — the `pi-timeout` input's value at the `INPUT_PI_TIMEOUT` → `CW_PI_TIMEOUT` links, then the 21600 code default, honoured as resolved — a declared value that leaves the stage's non-call work no headroom fails the run at trigger time with a precise error, and no stage runs after the trigger (the trigger validates the resolved job timeout against the resolved cap plus the headroom — 7200 seconds, the margin the stage's own non-call work needs around each call, derived from the two documented input defaults: the 480-minute default job timeout minus the 21600-second default pi call cap); a run that reaches a stage has validated the pair) — and every pi call in the pipeline rides that one resolution: the stages' generation calls, the guard's repair call, the PR-body call, the setup stage's smoke check;
