# 5. Solution Strategy

One reusable workflow (`factory.yml`), **9 jobs**, on the target repo's
runner — no pre-installed or pre-configured pi is a pre-requisite of that
environment: stage 2 installs pi for the run and configures it for the
workflow run from the run's provided harness.

| # | Stage | Job |
|---|---|---|
| 1 | trigger (label gate / dispatch / idempotency) | `trigger` |
| 2 | setup-pi (installs pi for the run, configures the run's harness, verifies the result) | `setup-pi` |
| 3 | baseline (cut/resume the AI branch, record the baseline) | `baseline` |
| 4+5 | requirement-extraction (+ guard) | `extract` |
| 6+7 | planning (+ guard) | `plan` |
| 8+9 | implementation (+ guard; a requirement edit is repaired in place) | `implement` |
| 10+11 | test & review (self-correcting loop) | `review` |
| 12 | open the pull request (the body describes the implemented issue; generated by pi) | `pr` |
| 13+14 | PR gates (+ fix loop; never merges) | `gates` |
| 15 | final status report (the PR is the report; the source issue closes on a successful run) | `report` |

Key mechanisms:

- **The guard idiom** — one shared "only X changed" check
  (`.github/scripts/guard-check.py` / `common.guard`) with three call
  sites (requirement-check, plan-check, implement-check), each with its
  own file set: the two earlier checks run the guard as a whitelist (only
  their dir may change), the implement-check runs it INVERTED — the
  implementation's lane is everything EXCEPT the protected set (requirements
  and the plans dir), with exactly the current issue's plan file re-allowed
  over it; a leaking stage is repaired with a pi call instead of being
  reverted by git and restarted — the guard names the off-limits files that
  changed, tells pi to revert the changes to them, and tells the stage's own
  work to stay valid against the task its initial instructions gave it — and
  a clean re-check lets the stage complete without re-running — the plan
  stage excepted, whose check re-runs the plan stage's generation on the
  guard's cleared repair (the guard records it in the state dir and
  re-checks the re-run; plan: "the plan stage may only touch its own plan
  file" — any other change is reverted and the plan stage re-runs) — the
  repair bounded by the loop caps (a repair cap exhausted without clearing
  the violation fails the stage with a report listing the violations, and a
  requirement edit never loops the run back to the plan stage).
- **Bounded loops.** Guard repair, review-fix and gate-fix loops stop when
  their problems are resolved or when they reach the `MAX_LOOPS` iteration
  cap (0 = no cap) — no token budget is one of the loops' stopping
  conditions; every stage's pi call carries its own time cap, and a call cut
  off at the cap (exit 124) is retried inside the loop — a slow model is not
  a broken environment. The five stage jobs that make pi calls run under the
  target's `job-timeout` input (default `480` minutes — a consumer that
  leaves the input undeclared keeps the 480-minute backstop, unchanged; the
  trigger and the setup-pi jobs are unaffected by the input; the stage code
  knows the same value through the shared plumbing) as their job-level
  `timeout-minutes`, which bounds how long the job a cut-off call retries in
  may run; a declared value that leaves the stage's non-call work no headroom
  fails the run at trigger time with a precise error, and no stage runs after
  the trigger — the trigger validates that the resolved job timeout exceeds
  the resolved pi call cap by at least the headroom (7200 seconds — the
  margin the stage's own non-call work — checkout, guard, loop machinery,
  artifact sync, push — needs around each call, and the margin the factory's
  own default pair already provides: the 480-minute default job timeout minus
  the 21600-second default pi call cap), the default pair passing at exactly
  the margin; a run that reaches a stage has validated the pair, and its pi
  calls honour the resolved value.
- **The context contract — two disjoint slices** (the oracle's two
  pinning scenarios are re-sliced onto disjoint stage boundaries): the
  *extraction* stage is the **`@`-file slice** — the arc42 markdown,
  `README.md` and the baseline diff are handed to pi as `@`-file arguments,
  which pi reads as context before answering (setup-pi: "pi reads the project
  files as context"); the Gherkin oracle is NOT one of those arguments — the
  instructions name the requirements directory as the oracle's location and
  list no requirement file by name, and pi reads the files it judges relevant
  from that directory on demand (a directory is never an `@`-argument — its
  handling reads files, so one there would crash pi with EISDIR); the *plan,
  implement, review and pr-body* calls keep the **path-referenced slice** —
  context files are only referenced by path in the invocation, their
  contents are never embedded in the prompt, pi reads the ones the task
  needs on demand with its read tool, and the invocation's token overhead
  stays small (configuration: "project files are referenced by path, not
  injected into the pi call"); the plan call's instructions additionally
  carry the delta — which requirement files changed and what those files
  changed — while the whole oracle stays out of the planner's context. One
  invocation never mixes the two.
- **State rides artifacts, never the tree.** Stage results (baseline
  ref/diff, trigger state, PR identity, per-iteration review logs and
  reviewer reports, resolved configuration) live in the state dir under
  `$RUNNER_TEMP` and travel as workflow artifacts; nothing under
  `test-results/` (or any other scratch) is ever committed.
- **Branch hygiene.** All writes land on `ai/code-weaver/<issue>`; a
  re-triggered run *reuses* the existing AI branch (a fresh cut happens
  only when the branch is absent); the target branch is never touched by
  the factory, and a broken stage cannot corrupt it. A completed
  stage's work is committed and pushed to the AI branch as part of
  stage completion — inside the stage machinery, not only the job's
  tail: the shared generation loop pushes after each clean iteration
  (the single-call stages' push at stage completion; the implement
  stage's push after each completed step, before the next step starts),
  the dependency-upgrade step pushes after its own commit, and the
  review stage pushes at its completion point — a run terminated after
  a stage completes loses none of the completed stage's work; the push
  fires only after the guard has passed (a violating iteration is never
  pushed — the remote branch stays at the last completed clean state),
  and a push that actually fails fails the stage (its work would not be
  on the remote, and the next stage or a re-trigger would lose it).
- **The project's dependency-install step.** The optional
  `dependency-install` input (the consumer's `with:` block) names a
  command, and the run's pipeline executes it in the two stage jobs
  whose stages consume the project's dependencies — the `implement` job
  (stage 8) and the `review` job (stage 10, the `make test` suite run)
  — after each of those jobs' checkout of the AI branch and before its
  stage, so both stages see an environment the dependencies are
  installed in. A target that declares nothing runs unchanged: where
  the input is empty the step is a no-op (it logs and exits 0 without
  touching the workspace), and the run is unchanged by the mechanism's
  presence. The step is inlined workflow text, not a new component —
  no new job is added, the 15-stage / 9-job pipeline count stays, and
  the self-contained shape is preserved.
- **The project's dependency-upgrade stage.** The optional
  `dependency-upgrade` setting (the consumer's `with:` block, like
  `max-loops`) decides whether the run's pipeline runs the
  dependency-upgrade stage: the stage upgrades the project's
  dependencies to newer versions, and it runs before the
  implementation stage. The setting's default is on; a target turns it
  off through its consumer workflow (a `dependency-upgrade: off` line
  in the `with:` block, like `max-loops`) — and where the setting is
  off the step is a no-op (it logs and exits 0 without touching the
  workspace): the pipeline runs without the stage, and the run's
  stages, pull request and final status report are unchanged by the
  upgrade's absence. The stage is an inlined step in the existing
  `implement` job (stage 8) — after its checkout of the AI branch and
  before the stage step and its stage-baseline recording, so the
  upgrade's footprint is never counted as the stage's work by the guard
  — and where the setting is on and the target has declared a
  `dependency-install` command, the step runs that command and commits
  the footprint to the AI branch, the only documented cross-job
  workspace channel: the consuming stages (the implementation stage,
  the `review` job's `make test` suite run) work against an upgraded
  project whose test suite still passes — the upgrade does not break the
  project's current functionality. As for the dependency-install step,
  it is inlined workflow text, not a new component — no new job is
  added, the 15-stage / 9-job pipeline count stays, and the
  self-contained shape is preserved.
- **The PR is the final report.** Stage 12 pushes the branch and opens the
  PR; its body is **generated by pi from the requirements, the plan and
  the review** (a template assembles the fallback when the pi call
  produces nothing). Stage 15 completes the body with the run status and
  comments the source issue. No merge call exists anywhere — merging
  stays a human decision.
