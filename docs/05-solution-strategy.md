# 5. Solution Strategy

One reusable workflow (`factory.yml`), **9 jobs**, on the target repo's
runner — a runner whose environment already has pi installed & configured
(stage 2 only verifies; the factory never installs or configures it).

| # | Stage | Job |
|---|---|---|
| 1 | trigger (label gate / dispatch / idempotency) | `trigger` |
| 2 | setup-pi (verify pre-installed pi) | `setup-pi` |
| 3 | baseline (cut/resume the AI branch, record the baseline) | `baseline` |
| 4+5 | requirement-extraction (+ guard) | `extract` |
| 6+7 | planning (+ guard) | `plan` |
| 8+9 | implementation (+ guard; requirement edits loop back to plan) | `implement` |
| 10+11 | test & review (self-correcting loop) | `review` |
| 12 | open the pull request (body generated by pi) | `pr` |
| 13+14 | PR gates (+ fix loop; never merges) | `gates` |
| 15 | final status report (the PR is the report) | `report` |

Key mechanisms:

- **The guard idiom** — one shared "only X changed" check
  (`.github/scripts/guard-check.py` / `common.guard`) with three call
  sites (requirement-check, plan-check, implement-check), each with its
  own allowed path set. A leaking stage is reverted to its baseline and
  re-run, bounded by the loop caps.
- **Bounded loops.** Guard re-run, review-fix and gate-fix loops respect
  `MAX_LOOPS` (0 = no cap) and the `MAX_TOTAL_TOKENS` budget; every
  stage's pi call carries its own time cap, and a call cut off at the cap
  (exit 124) is retried inside the budget — a slow model is not a broken
  environment.
- **The context contract — two disjoint slices** (the oracle's two
  pinning scenarios are re-sliced onto disjoint stage boundaries): the
  *extraction* stage is the **`@`-file slice** — its context (the Gherkin
  oracle, the arc42 markdown, `README.md`, the baseline diff) is handed to
  pi as `@`-file arguments, which pi reads as context before answering
  (setup-pi: "pi reads the project files as context"); the *plan,
  implement, review and pr-body* calls keep the **path-referenced slice** —
  context files are only referenced by path in the invocation, their
  contents are never embedded in the prompt, pi reads the ones the task
  needs on demand with its read tool, and the invocation's token overhead
  stays small (configuration: "project files are referenced by path, not
  injected into the pi call"). One invocation never mixes the two.
- **State rides artifacts, never the tree.** Stage results (baseline
  ref/diff, trigger state, PR identity, per-iteration review logs,
  resolved configuration) live in the state dir under `$RUNNER_TEMP` and
  travel as workflow artifacts; nothing under `test-results/` (or any
  other scratch) is ever committed.
- **Branch hygiene.** All writes land on `ai/code-weaver/<issue>`; a
  re-triggered run *reuses* the existing AI branch (a fresh cut happens
  only when the branch is absent); the target branch is never touched by
  the factory, and a broken stage cannot corrupt it.
- **The PR is the final report.** Stage 12 pushes the branch and opens the
  PR; its body is **generated by pi from the requirements, the plan and
  the review** (a template assembles the fallback when the pi call
  produces nothing). Stage 15 completes the body with the run status and
  comments the source issue. No merge call exists anywhere — merging
  stays a human decision.
